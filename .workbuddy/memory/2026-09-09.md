## 修复：Navidrome / WebDAV 远程曲目的歌词获取链路

现象（诊断结论）：`lyrics_service.dart` 里虽然写了「优先取服务端歌词」的分支
（`fetchBestLyrics()` 中 subsonic:// / webdav:// 的 `_remoteLyricsFetcher`），
但实际播放流程从没走到过 —— `LyricsController.build()` 自己 new 了一个没注入
fetcher 的 `LyricsService`，只有 `lyricsServiceProvider` 那个实例带了 fetcher，
而后者只被「在线歌词搜索」对话框用到，且只调 `scoreAndSortTracks()`。

改动（4 个文件，`flutter analyze` 无新增问题）：

1. `lyrics_controller.dart`：`_lyricsService` 改为 `ref.read(lyricsServiceProvider)`，
   与 provider 共用实例（MetadataDatabase 是单例，缓存库换实例也安全）。
2. `lyrics_riverpod.dart`：`remoteLyricsFetcher` 签名由 `(String uri)` 改为
   `(LyricsQuery query)`，构造 MusicFile 时带上 title/artist/album。
   原因：`RemoteMediaResolver.fetchLyrics()` 回退到 `getLyrics.view` 时依赖
   artist+title，之前传的是空壳 MusicFile，必然查空。
3. `subsonic_client.dart`：
   - `getLyrics.view` 读的是 `lyrics['content']`，而 Navidrome 的
     `responses.Lyrics` 序列化出来是 `{artist, title, value}` → 改为 `value ?? content`。
     参考 `navidrome/server/subsonic/responses/responses.go:513-517`。
   - `getLyricsBySongId` 分支：从「只取第一条」改为遍历选第一条有内容的、
     且优先 synced 的；无 start 时输出纯文本而不是拼成 `[00:00.00]` 假逐行歌词
     （Navidrome 对无时间轴歌词会省略 start）。
4. `lyrics_service.dart`：新增 `_cacheRemoteServerLyrics()`，服务端歌词命中后
   以 `LyricsCacheSource.external` 落 SQLite（不新增枚举值，避免波及 sharing_service
   的优先级映射等穷举 switch）。不落缓存的话后续 LRCLIB 结果会反过来抢在服务端歌词前面。

备注：Navidrome 服务端歌词来源由 `ND_LYRICS_PRIORITY` 决定
（`navidrome/core/lyrics/lyrics.go:89`）：embedded → 同名 .lrc → 插件。
