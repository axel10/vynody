## 修复：Android 竖屏二级页转场时双 Dock 同屏

- 现象：媒体库首页点艺术家/专辑等卡片进入详情页，Android 竖屏转场动画期间底部短暂多出一个浮动 Dock 栏，动画结束后消失。
- 根因：MainLayout 竖屏常驻一个全局 `FloatingDockBottomBar`（main_layout.dart ~1578），而所有二级详情页根部包了 `MiniPlayerWrapper`（artist_detail_page.dart:96 等），后者竖屏时又自渲染一个新 Dock（mini_player_wrapper.dart）；push 走 `MaterialPageRoute` + Android `ZoomPageTransitionsBuilder`（main.dart:627），转场期间新旧 route 同帧绘制，两套 Dock 同屏，动画结束后新 Dock 落位遮住旧 Dock，形成"多出的 Dock 消失"假象。
- 修复（方案 A）：`mini_player_wrapper.dart` 监听所在 `ModalRoute.animation` 的 status，转场未 completed 期间 Dock 用 `AnimatedOpacity`(0) + `AnimatedSlide`(offset 0,0.35) + `IgnorePointer` 隐藏，转场结束后 220ms 淡入上滑落位。横屏 sidebar 模式不渲染 Dock，不受影响。
- `flutter analyze lib` 验证：mini_player_wrapper.dart 零问题（117 个均为其他文件存量 issue）。
- **返工**：首版用 `AnimatedSlide`+`AnimatedOpacity` 包裹 Dock 导致进三级页崩溃 `type 'ParentData' is not a subtype of type 'StackParentData'`——`FloatingDockBottomBar` 根节点是 `AnimatedPositioned`，必须保持为 Stack 直接子级，不能被渲染层 widget 包裹。改用其自带 `isHidden` 入参：转场未完成时传 true（Dock 首帧直接定位在屏幕外），完成后传 false，内部 300ms 自行滑落+淡入到位。

## 修复：媒体库二级/三级页面多选「一进入就立刻退出」

- 现象：媒体库内艺术家页/专辑页/流派页/年份页等多选，一进入就立即退出（面板只闪一帧）。
- 根因：这些页面把 `PopScope` **条件性**地包在根节点上，多选开关会让根节点类型
  `AutoHideHeaderScope` ↔ `PopScope` 变化。Flutter 对同位置 runtimeType 不同的 widget
  无法复用 element，会 deactivate 旧子树并在 `finalizeTree` 里 unmount，
  于是整棵子树（含所有子 tab 的 State、横屏内嵌的 `ArtistDetailContent`）被 dispose。
  `SongSelectionMixin/SelectionStateMixin.dispose` 用 `Future.microtask(clearIfScope(scope))`
  收尾 → 微任务在帧后执行，正好把刚建立的多选状态 clear 掉。
  关键：**持有选中项的 widget 本身就在被销毁的子树里**，所以必然自杀。
  附带影响：每次进/出多选都会重建整棵子树 → 搜索词/排序/缓存列表/滚动位置全部丢失。
- 修复（统一 5 处，全部改为 PopScope 常驻、只切 `canPop`）：
  `library_page.dart` `_LibrarySubHostPageState.build`（最关键，整库二级页总壳）、
  `album_detail_page.dart`、`artist_detail_page.dart` `_ArtistDetailContentState.build`、
  `genre_detail_page.dart`、`folder_detail_view.dart`。
- 正确范式参考（项目里原本就对）：`remote_folder_browser_page.dart:1844`、
  `remote_control_page.dart:249`、`sharing_page.dart:721` 都是 `canPop: !xxxMode` 的常驻写法。
- 验证：写临时 widget 测试用真实 `SongSelectionMixin` + `librarySelectionStateProvider` 对比两种写法，
  旧写法点一下回落 IDLE（复现），新写法保持 ACTIVE（修复），两条断言均通过后删除测试文件；
  `flutter analyze lib` 五个改动文件零 issue。

## 排查：Android 返回上一级时，被点击入口残留高亮/水波纹

现象：点击媒体库首页入口进子页 → 按返回，被点击的入口在整个返回动画期间呈高亮态，动画结束后消失。
只出现在 Android（以及同样配了 Zoom 转场的 Windows/Linux），iOS/macOS 无此现象。

结论：不是业务逻辑 bug，是三条 Flutter 机制叠加：

1. `MaterialPageRoute` 过渡（300ms）完成时，新路由 entry 的 `opaque` 置 true，
   `Overlay.build` 会把被完全覆盖的下层 entry 包进 `TickerMode(enabled: false)`
   （`overlay.dart:907` → `:420`）。下层页面的动画**停 tick 但不会销毁**，
   ink feature 因此冻结在中途 —— 而 ink 动画总时长远超 300ms：
   Android M3 默认 `InkSparkle` 617ms（`ink_sparkle.dart:182`），`InkRipple` 为 225+375ms。
2. 返回时上层 route 状态转 reverse → 其 entry `opaque = false` → 下层 TickerMode 恢复。
   但 ticker 只是被重新 schedule，**本帧不会 tick**（要等下一次 `handleBeginFrame`），
   所以恢复绘制的第一帧，下层画面仍是「水波纹未退」的旧状态。
3. `lib/main.dart:625` 的 `pageTransitionsTheme` 给 android/windows/linux 配了
   `ZoomPageTransitionsBuilder`，其 `_ZoomExitTransition` 用 `SnapshotWidget`
   （`page_transitions_theme.dart:351`；`_ZoomTransitionBase.onAnimationStatusChange`
   在动画进行中置 `allowSnapshotting = true`，见 `:964`）——它会截下下层页面的当前画面，
   **整个返回动画期间都用这张静态图渲染**。于是那张「带水波纹」的帧被定格播完 300ms；
   动画结束、快照撤下、实时渲染接管时，ink 动画已跑到终点，高亮随之消失。
   Cupertino 转场不用 SnapshotWidget，所以 iOS/macOS 看不到。

反向验证点：宽屏下那排横向快捷卡（`library_dashboard_view.dart` 的 `_WideQuickCard`）
用的是 `GestureDetector` + `MouseRegion` hover、没有 ink 反馈，因此不出现该现象；
窄屏的竖条菜单项（同文件 `:715` 的 `InkWell`）才会。

可选修法（尚未动手）：
- A `ZoomPageTransitionsBuilder(allowSnapshotting: false)`——保留缩放转场与点击反馈，
  代价是转场期间每帧实时渲染（`_ZoomPageTransitionNoCache` 路径）。
- B 逐条路由 `MaterialPageRoute(allowSnapshotting: false)`，精准但每处都要写。
- C 主题 `splashFactory: NoSplash.splashFactory`——直接去掉水波纹，不推荐。

已验证并落地：android builder 先临时换成 `FadeUpwardsPageTransitionsBuilder()` 真机跑，
**残留高亮消失 → 根因确认为 Zoom 的 `SnapshotWidget`**。最终按方案 A 落地 ——
`lib/main.dart` 的 android 改为 `ZoomPageTransitionsBuilder(allowSnapshotting: false)`
（缩放转场与点击水波纹都保留，仅转场期间改为实时渲染），带注释说明原因。
windows/linux 仍是默认的 `ZoomPageTransitionsBuilder()`（同一机制在桌面端理论上存在，未改动）。
`flutter analyze --no-pub lib/main.dart` 通过，唯一告警是既有的 unused import。

## 播放页（PlaybackPage）出现/离开动画性能审查（只读诊断，未改任何代码）

用户问「播放页的出现和离开动画性能如何」。读 `main_layout.dart`（抽屉控制器 260-302、渲染 1629-1686）
与 `playback_page.dart`（手势 124-196、转场包裹 1614-1620）后确认三条路径：

1. **出现**：`_onDestinationSelected(1)` → `_expandPlayback()`（main_layout.dart:260）。
   `setState(_isPlaybackDrawerOpen=true)` 与 `animateTo(380ms, Cubic(0.2,0,0.15,1))` 在**同一帧**发生
   → PlaybackPage 就在这一帧首次 build。渲染走 `AnimatedBuilder(child: PlaybackPage)` +
   `Transform.translate(0, (1-progress)*h)`（:1637-1655），PlaybackPage 作为缓存 child **不 rebuild**。
2. **离开**：`_collapsePlayback()`（:279）→ `animateTo(0, 280ms, easeInQuad)`，**`.then` 之后才**
   `setState(_isPlaybackDrawerOpen=false)`，即动画结束才把 PlaybackPage 从树上摘掉。
3. **手势下滑**：`_handleVerticalDragUpdate` 每帧 `setState(_dragOffsetY)`（playback_page.dart:136）；
   松手过阈值后 `_dismissAnimController`（260ms）的 listener 也每帧 `setState`（:281-287），
   跑完才 `_triggerCollapse(animated:false)` 无动画收外层。

### 发现的问题点

- **A. Transform.translate 是纯平移 → 不产生合成层。** Flutter 的 `RenderTransform.paint` 只在变换
  不等于纯平移时才 `pushTransform`；纯平移时直接 `super.paint(context, offset + childOffset)`。
  而 PlaybackPage 的 return 链（`Listener → OrientationBuilder → Transform.translate → Container → Stack`，
  :1033 / :1614-1620）**顶层没有 RepaintBoundary**，所以滑入/滑出期间每帧都重走整棵子树的 paint。
  内部已有的 RepaintBoundary（背景 :1794、content :1469、visualizer :72）能复用 layer；
  但背景外层裹着 `AnimatedOpacity`+`AnimatedSwitcher`（:1263-1280）、scrim（:1722）、
  small_win 层（:1282-1305）没有 boundary，仍会重绘（都是纯色/渐变，单帧成本低）。
- **B. 真正的成本在首帧**：同一帧里 setState + 首次 build，要做完整页 build（OrientationBuilder +
  LayoutBuilder + 十几个 ref.watch）、CoverCarousel 封面解码、`_buildBackgroundWidget` 被调两次
  （normal :1271 / small_clear :1296，各带 800ms AnimatedSwitcher）、模糊背景光栅化。
  作者已做补救：`_heroWarmupTimer` 延后 320ms 才 `completeHeroTransition()`（:312-316）。
- **C. 320ms 预热与 380ms 进场动画不匹配**（:311 注释写「main layout transition is 320ms」，
  实际进场 380ms / 离场 280ms，且是硬编码魔数、未共享常量）。进入动画**尾段 60ms** 会跑
  `completeHeroTransition()`：`_queueProcessor.resume()` + `scanner.resumeBackgroundTasks()` +
  `_startQueueBackgroundProcessing()` + `audioService.notifyListeners()`（广域通知），压在动画尾段。
- **D. 离开即销毁**：连带后果是「反复进出永远满额成本」——`_pendingArtworkPath`、`_coverKey`、
  封面轮播位置、歌词滚动位置每次重置，成本不随次数摊薄。
  `dispose()` 里还有两处 `Future.microtask`（:334-346）会跨帧落到下一次交互上。
- **E. 手势路径最重**：`_dragOffsetY` 只被最外层一个 `Transform.translate` 消费（:1614-1618），
  却让整个 PlaybackPage 每帧全量 build，属于「值提升过深」。

### 候选优化（未动手，待用户拍板）

1. PlaybackPage 顶层加 RepaintBoundary → 滑入/滑出只更新 layer offset（代价：一块全屏 layer 显存）。
2. `_dragOffsetY` 改 `ValueNotifier` + 只让最外层 Transform 订阅 → 拖拽/回弹不再整页 rebuild。
3. hero 预热 timer 改为跟 `_expandPlayback` 实际时长对齐（抽常量或改成动画结束回调）。

未做真机 profile，结论均为代码层静态审查。用户未要求改代码。

## 播放页动画掉帧：DevTools timeline 实测分析（用户提供导出数据）

用户反馈「播放页出现/离开动画有时卡有时不卡」并给了 DevTools 导出

格式是 DevTools snapshot：`performance.flutterFrames`（193 帧，字段 number/startTime/elapsed/build/raster/vsyncOverhead，**微秒**）；
`performance.traceBinary` 为空、`rebuildCountModel` 为 null → **只有帧级汇总，没有 CPU profile / timeline events**。

### 数据事实（3.98s / 193 帧，1600×，预算 16667us）

| 指标 | 中位数 | 均值 | 最大 |
|---|---|---|---|
| elapsed | 13558 | 15282 | 77638 |
| build | 1320 | 3329 | 69731 |
| raster | 9780 | 9673 | 15184 |

- 超预算帧 34/193 = **17.6%**；掉 1 帧的 9 个，掉 ≥2 帧的 1 个。平均 20.6ms/帧 ≈ 48fps。
- **raster 中位数 9.78ms、41% 的帧 >10ms，但从不单独超预算**（最高 15.18ms）→ 渲染线程长期吃 60–90% 预算，
  这是「基线高」的来源，与前面查到的「模糊背景每帧重绘」（纯平移 Transform 不建合成层 + 页面顶层无 RepaintBoundary）一致。
- **build 平时只有 ~1ms，但每 ~250ms 出现一次 15–70ms 尖峰**（18 帧 >10ms）。间隔极规律：
  1664→1678→1692→1706→1720→1747→1761→1775→1789 全部 242–258ms。
- 尖峰帧的 raster **反而偏低**（5000–7500 vs 普通帧 9000–14000）→ 尖峰发生在「画面简单/动画未跑」的时刻，
  符合「周期性定时器驱动的 rebuild」而非「动画本身重」。

### 250ms 节拍的来源（代码可证）

`android_integration_service.dart:101-136` `updateTimeline()` 的 `shouldForward` 里
`elapsed >= const Duration(milliseconds: 250)`（:114）—— Android 播放进度上报节流就是 250ms，
底层回调频率更高所以几乎每次都恰好卡在 250ms 上转发 → `_handler.onPositionChanged()` →
`AudioService.notifyListeners()`（`AudioService` 本体就是 `NotifierProvider<AudioService, AudioSnapshot>`，
audio_riverpod.dart:42）。

一次 notifyListeners 的成本链：
1. Riverpod 读 `state` = `AudioService.snapshot` getter（audio_service.dart:1967-1998）；
2. `AudioSnapshot` 是 @freezed（audio_snapshot.dart），`==` 由 freezed 生成，集合字段用
   `const DeepCollectionEquality().equals(...)` —— playbackQueue / randomHistory / randomQueue / currentThemeColorsMap 四处；
3. **`queue` 不是缓存字段而是 getter**（audio_service.dart:117-121）：
   `_player.playlist.items.map(_musicFileForTrack).whereType<MusicFile>().toList(growable:false)`，
   每次访问都全量重建；`_queue => queue`（:124）又是一层转发；
4. `randomHistory`（:2089）里每个 entry 访问 `_queue` **2 次**（`_queue.length` + `_queue[i]`，fallback 时 +1 次 `firstWhereOrNull` 扫描）；
   `randomQueue`（:2104）每个 id 1 次 `_queue` + `firstWhereOrNull` O(n) 扫描；
   `snapshot` 自身 `List.unmodifiable(_queue)` 再 1 次。
   → 一次 snapshot = **(h×2 + d + 1) 次全队列重建**，h=history 长度、d=deck 长度、n=队列长度。
5. 另外 `AudioPlaybackQueueNotifier`（audio_riverpod.dart:114-119）的 `ref.listen` 里再跑一次
   `listEquals(previous.playbackQueue, next.playbackQueue)`，O(n) 次 `MusicFile.==`。

### 重要的负结论（避免下次误判）

`_musicFileForTrack` 走 `track.metadataValue<MusicFile>('musicFile')`，
而 `metadataValue` 只是 `metadata[key]` 的纯 Dart Map 查找（audio_core/lib/src/playlist_models.dart:39-42），**不是 FFI**。
按上述结构复刻的微基准（/tmp/vynody_perf/bench.dart，n=500/2000、h=d=30/50）实测：
- 一次 `snapshot()` 全流程 **205–456us**（含重复全队列重建 + unmodifiable 复制）
- 单项对照：只构造一次 queue + unmodifiable = 2–7us；`DeepCollectionEquality` 逐元素比较 500 首 = 7us

**即 snapshot getter 与 == 判等合计只有几百微秒，不是 15–30ms 的来源。** 大头在**下游 widget 的 rebuild**，
而这份导出没有 CPU profile，**无法定位到具体函数/widget**。不要在没补数据前把矛头全指向 snapshot getter。

### 关于「有时卡有时不卡」

尖峰的**间隔**很稳（250ms ±8ms），但**幅度抖动近 6 倍**（11ms → 70ms）。所以：
- 380ms 的动画窗口必然跨过 1–2 个 250ms 尖峰，但尖峰落在动画哪个相位取决于按下时刻相对音频进度定时器的相位偏移，随机；
- 决定观感的是「那一次尖峰有多大」+「落在动画哪一段」，两个变量都在抖 → 主观上就是有时卡有时不卡。
- 两个异常大的尖峰：#1629（69731us）和 #1794（30055us），疑似对应 PlaybackPage 首次构建 / 销毁那一帧。

### 已确认可优化的点（尚未动手）

1. `lib/widgets/equalizer_panel.dart:55` `final snapshot = ref.watch(audioSnapshotProvider);` —— **全项目唯一一处裸 watch 整个 snapshot**，
   每次 position 变化都会整面板 rebuild。应改 select 或 `ref.read` + 局部 listen。
2. `AudioService.queue` 改成缓存字段 + 版本号失效（现在是 getter，每次访问全量重建）。
3. `randomHistory` / `randomQueue` 把 `_queue` 提到局部变量（避免 lambda 内重复求值）、且只在随机模式下计算；
   更好的做法是不放进 `AudioSnapshot`。
4. `snapshot` 里的 `List.unmodifiable(...)` 换成稳定引用 + revision 参与判等（同 `ScannerService.structureRevision` 的思路）。
5. 治本方向：把 `position` 从 `AudioSnapshot` 剥离成独立的轻量 notifier/provider，
   让 250ms 的高频更新不再把整个巨型 snapshot 判为「已变化」。
6. 前面那节的 A/C 两条（PlaybackPage 顶层 RepaintBoundary、`_dragOffsetY` 改 ValueNotifier）依然成立，作用于 raster 基线。

用户未拍板改哪条，代码未动。

- 语义树构建+上报 **14.2%**，其中引擎 FFI `FlutterView.__updateSemantics` 一项就 **9.1%**（全 profile 自耗第一）

### 结论
1. **卡在开头一帧，不是卡在整段动画**：重活集中在前 3 帧的整树 rebuild。
2. **嫌疑主因在 `main_layout.dart`**：`MainLayout.build()` 里 watch 了 6 个 provider，

3. **semantics 全程开启**：`flushSemantics` 占全 profile 26.6%（去重口径）、动画稳态期占帧内 40–60%。
   而项目**自身没有任何 `ensureSemantics` / `SemanticsHandle`**（已全库 grep 确认）。
   → 来源需用户确认：真机无障碍服务（TalkBack/自动点击器/录屏类）还是 DevTools 侧。
   若是设备侧，这属于真实用户场景；整页 `Transform.translate` 滑动会让语义树几何每帧失效、全量重传，

4. 采样器自开销（`_reportTaskEvent` 7.9%）+ 栈截断，是这份数据的两个硬限制。

## Android 播放时 logcat 被 `V/jni::wrapper::jnienv` 刷屏（根因定位，未改代码）

现象：播放时持续输出 `calling unchecked jni method: GetDirectBufferAddress/Capacity` +
`looking up jni method X` + `found jni method`。

根因链（已逐层验证）：
1. `controller.rs:1989 init_app()` **无条件**调用 `flutter_rust_bridge::setup_default_user_utils()`；
   desktop 分支的 `env_logger` 是 `cfg(any(windows,linux,macos,ios))`，**Android 不在此列**，
   所以 Android 上唯一的日志后端来自 frb。
2. frb 2.11.1 `src/misc/user_utils.rs:26-29`：Android 分支执行
   `android_logger::init_once(Config::default().with_max_level(LevelFilter::Trace))`
   → 全局门槛被拉到 Trace，logcat tag 取 `module_path!()`（故显示为 `jni::wrapper::jnienv`）。
3. `jni` 0.21.1 `src/wrapper/macros.rs`：`jni_method!` 打 `looking up jni method X`(L66) +
   `found jni method`(L70)，`jni_unchecked!` 打 `calling unchecked jni method: X`(L56)，
   全为 `log::trace!` → 每次 direct buffer 调用 3 行。
4. 唯一高频 direct buffer 调用点：`equalizer.rs:885` / `:888`
   （`Java_..._CppEqualizerProcessor_nativeProcess`），
   Kotlin `CppEqualizerProcessor.kt:120` 在 ExoPlayer 每个音频缓冲里调一次，**不受 EQ 开关约束**
   （只判 `nativeHandle != 0`）→ 每缓冲 6 行，每秒数十次。

结论：纯日志噪音，不是错误。候选修复（待用户定）：
A. `init_app()` 里 Android 分支在 `setup_default_user_utils()` **之前**自己
   `android_logger::init_once(...)`（once-only，先到先得），设 Info/Debug + `with_filter` 屏蔽 jni 模块；
B. 一行版：`setup_default_user_utils()` 之后 `log::set_max_level(LevelFilter::Info)`，
   全局门槛降到 Info，`trace!` 在宏处短路，开销归零，且与桌面端 env_logger 行为一致
   （代价：Android 上 debug 级日志也没了）。
注意 `audio_core` 的 Cargo.toml 已声明 `android_logger = "0.15.0"` 但 src 里无人使用。

### 已按方案 A 落地（2026-10-16 22:05）

- `rust/src/lib.rs`：新增 `#[cfg(target_os = "android")] pub(crate) fn init_platform_logger()`，
  level = `cfg!(debug_assertions) ? Debug : Info`，先 `android_logger::init_once(Config::default().with_max_level(level))`
  再 `log::set_max_level(level)`。
- **两处 init 入口都要调**（`setup_default_user_utils()` 之前）：
  `api/simple/controller.rs::init_app`（Dart 侧 visualizer_player_controller.dart:287 显式 await）
  和 `api/audio_converter/simple.rs::init_app`（`#[frb(init)]`，frb 自动调用，顺序不确定）。
  两处都调 + `set_max_level` 兜底 ⇒ 与调用顺序无关。
- 关键技术事实：`android_logger 0.15.1` 的 `init_once` 是 `ANDROID_LOGGER.get_or_init` 语义，
  只对**第一个**调用者生效（后调用者 `set_logger` 失败即静默返回，且**不会**再改 max_level）；
  但 `log::set_max_level` 是全局原子，后写生效 —— 所以兜底那行才是顺序无关的保证。
- 验证方式：Android 交叉编译环境可本地复现（Gradle/cargokit 注入了什么，见
  `cargokit/build_tool/lib/src/android_environment.dart:177-195`：`FFMPEG_DIR` =
  `android/ffmpeg_lib/<abi>`，另有 CC/CXX/AR/BINDGEN_EXTRA_CLANG_ARGS 指向 NDK clang）：
  ```
  NDK=$HOME/Library/Android/sdk/ndk/28.2.13676358
  FFMPEG_DIR=.../audio_core/android/ffmpeg_lib/arm64-v8a \
  CC_aarch64_linux_android=$NDK/toolchains/llvm/prebuilt/darwin-x86_64/bin/aarch64-linux-android24-clang \
  CXX_aarch64_linux_android=...clang++ AR_aarch64_linux_android=.../llvm-ar \
  CFLAGS_aarch64_linux_android="--target=aarch64-linux-android24 --sysroot=$NDK/.../sysroot" \
  BINDGEN_EXTRA_CLANG_ARGS_aarch64_linux_android="同上 + -isystem .../sysroot/usr/include" \
  cargo check --target aarch64-linux-android --lib
  ```
  **不设 `FFMPEG_DIR` 会卡在 `ffmpeg-sys-next` 的 pkg-config 交叉编译报错**（ffmpeg_lib 里的
  `*.pc` prefix 指向 CI 的 `/home/runner/...`，本地不可用，必须靠 FFMPEG_DIR 绕过 pkg-config）。
  `cargo check` 不链接，故无需 libgcc workaround 与 linker wrapper。
- 结果：Android 目标 `cargo check` 通过，无新增警告（`rustfmt --check` 也过）。
