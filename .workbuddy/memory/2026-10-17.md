# 2026-10-17

## 媒体库首页性能审查（只读分析，未改代码）

排查 `lib/pages/library_dashboard_view.dart` 及其数据链路的阻塞点。核心结论：**问题不在单次查询慢，而在「一次 songs 表写入 → 6 路全表重算」的放大器结构，且首页常驻。**

### 关键事实（带位置）

- 首页共订阅 **6 路** 基于 `MetadataDatabase().watchAllSongMetadata()` 的流：
  `albumLibraryProvider`(album_library.dart:11)、`artistLibraryProvider`(artist_library.dart:14)、
  `genreLibraryProvider`(library_overview_providers.dart:39)、`yearLibraryProvider`(:121)、
  `allRatedSongsProvider`(:261)、`timeMachineAlbumsProvider`(:321)。
- **只有 album / artist 加了 `.throttleLeadingAndTrailing(1s)`**（album_library.dart:33、
  artist_library.dart:66）；genre / year / allRated / timeMachine 四路无节流。
  节流实现见 `lib/utils/stream_utils.dart`。
- `watchAllSongMetadata()` 是 drift `customSelect` + `ORDER BY LOWER(path) ASC`
  （metadata_drift_database.dart:818），函数排序走不了索引，每次变更都全表重排；
  `_songFromQueryRow`(:2799) 每行还做 3 次 `IosPathManager.resolveSandboxPath` + `jsonDecode(genres)`。
- **触发源极高频**：`scanner_service.dart:413 updateSongThumbnailPath` → `insertOrUpdateSong` 写 songs 表，
  调用点是 `song_thumbnail.dart:151/164`（每张缩略图生成后回调）。所以「首屏渲染出缩略图」本身就会
  反复捅这个放大链路。（scanner 侧的 notify 有 150ms 节流 + structureRevision 指纹，DB 侧没有。）
- **首页常驻**：dashboard 是 `library_page.dart:229` 的 Navigator 栈底路由，推入二级页后仍在树上；
  MainLayout 的 IndexedStack 也让整个媒体库页常驻。→ 人不在首页时这套成本照付。
- section 用的 `_cachedXxx` 快照（ref.listen + `if (_cached == null)`）**只省了 UI 重建，没省 provider 计算**，
  订阅一直活着。
- 与之相反，`_DashboardHeader` / `_WideQuickAccessBar` / `_PortraitLibraryMenuCard` 是
  `ref.watch(genre/yearLibraryProvider).value?.length` —— StreamProvider 每次 emit 新的 `List` 实例，
  `AsyncData` 判等失败 → 这三处必重建（快捷入口栏重建 9 张卡片）。
- 纯 `Provider`（同步）在 build 阶段做重活：`mostPlayedAlbumsProvider`(:438)、
  `recentlyAddedAlbumsProvider`(:680)、`topRatedAlbumsProvider`(:733)，其中 mostPlayedAlbums 是
  双层循环（所有专辑 × 专辑内所有歌，:476-487），由 section build 里的 `ref.read` 同步触发。
- 循环内低效写法：`library_overview_providers.dart:75` 和 `:154` 用
  `s.path.split(RegExp(r'[/\\]')).last` 逐行新建正则（album_library 用的是 `p.basename`，正确）。
- 同步 IO 在 build 里：`_ArtistsRowSection._prefetchDisplayedArtists` 对 12 个艺术家逐个
  `File(...).existsSync()`；`_DashboardArtistItem.initState` 同样 existsSync + 发起 TheAudioDB 网络请求。
- `_RecentlyPlayedSection` 的 itemBuilder 内 `previewItems.map((e) => e.song).toList()`（:1117 附近）
  每项重建整表，20 项，O(n²) 分配但量级很小。

本次已实施 ①③④，② 与「聚合下沉 SQL / isolate」未做：

## 已落地的改动（①③④）

**`lib/player/library/library_overview_providers.dart`**
- 新增 `import 'package:vynody/utils/stream_utils.dart';`
- 四路补 `.throttleLeadingAndTrailing(const Duration(seconds: 1))`：
  `genreLibraryProvider`、`yearLibraryProvider`、`allRatedSongsProvider`、`timeMachineAlbumsProvider`。
  与 album_library.dart:33 / artist_library.dart:66 完全一致（leading edge 立即出首帧，
  后续 1s 内合并）。**注意规律：凡是 `StreamProvider` 里 `await for (db.watchAllSongMetadata())`
  都必须带这层节流**，否则扫描/缩略图回写期间会逐条重算。
- 两处 `s.path.split(RegExp(r'[/\\]')).last` → `p.basename(s.path)`（genre:80、year:161）。
  `p.basename` 在 Windows 上会走 windows context，反斜杠路径同样正确。
- 结论：`topRatedSongsProvider`(:209) 与 `timeMachineSongsProvider`(:584) 全项目只定义无引用，
  是死代码，未加节流。剩下这两处 `watchAllSongMetadata()` 未节流，将来若启用需补。

**`lib/pages/library_dashboard_view.dart`**
- 三处头部计数由 `ref.watch(xxxProvider).value?.length` 改成
  `ref.watch(xxxProvider.select((v) => v.value?.length))`：`_DashboardHeader`（含 playlists）、
  `_WideQuickAccessBar`、`_PortraitLibraryMenuCard`。
  原因：StreamProvider 每次 emit 的是新 `List` 实例，整份列表 watch 必然重建（横屏快捷栏一次重建 9 张卡）。
- `playlistServiceProvider` 是 `ChangeNotifierProvider<PlaylistService>`，同样用 select 出
  `playlists.length` 只订阅计数。

## 已落地的改动（②：曲库单一数据源）

用户拍板：artist 并入 / 删死代码 / 过滤语义保持原样。

**新增 `lib/player/library/library_catalog.dart`**
- `class LibraryCatalog`：持有 `songs`（已排除 external + deletedAt）与 `isPathAllowed` 闭包；
  字段全部 `late final` 惰性求值 —— `visibleSongs`（套用活动根目录 + 来源过滤）、
  `albums`、`genres`、`years`、`artists`（Future，需查两张 artist 缓存表）。
  **惰性化是这套方案不产生回归的前提**：只打开年份页就只算年份。
- `libraryCatalogProvider = StreamProvider<LibraryCatalog>`：**全应用唯一的 songs 表订阅点**。
  4 个 scanner select + `librarySourceFilterProvider` 只在这里 watch 一次。
- `Stream<T> catalogDerived<T>(Ref ref, FutureOr<T> Function(LibraryCatalog) select)`：
  把快照包成 Stream，让派生 provider 保持 `StreamProvider<...>` 类型与 `overrideWith` 签名不变
  （这是测试不用改的关键）。select 允许返回 Future 以支持异步的艺术家聚合。
- 私有 `_buildGenreSummaries` / `_buildYearSummaries` 从原 provider 搬来（去掉过滤，只做聚合）。

**`album_library.dart`**：`albumLibraryProvider` 改为一行 `catalogDerived`；
`buildAlbumSummaries` 仍留在本文件（`audio_service.dart:3331/3554` 在用）。

**`artist_library.dart`**：
- `artistLibraryProvider` 改为 `catalogDerived(ref, (catalog) => catalog.artists)`。
- 新增公开方法 `ArtistLibraryRepository.buildSummariesFor(Iterable<SongMetadata>)`，
  聚合实现唯一；`watchArtistSummaries()` 改为复用它，并**去掉 `isPathAllowed` 参数**
  （调用方 `audio_service.dart:3354/3578` 本来就是无参调用）。
  该方法保留是因为 audio_service 的「播放下一首/上一首艺术家」要走它 —— 那条路径每次仍会全表扫一次，
  属低频操作，本次未动。

**`library_overview_providers.dart`**：
- `genreLibraryProvider` / `yearLibraryProvider` / `allRatedSongsProvider` / `timeMachineAlbumsProvider`
  全部改为 `catalogDerived` 派生。
- **删除死代码 `topRatedSongsProvider`、`timeMachineSongsProvider`**（全项目仅有定义、无引用）。
- 打分/播放数据仍各自 watch：`songRatingServiceProvider`（ChangeNotifierProvider）、
  `mostPlayedSongsProvider`。收益是打分后只重跑内存计算，不再重扫全表。
- 过滤语义按用户要求**保持原样**：`allRatedSongsProvider` 与 `timeMachineAlbumsProvider`
  用 `catalog.songs`（不过滤活动根目录/来源），其余用 `catalog.visibleSongs`。
  这个不一致本身仍是待办。

**留下的已知事实**
- `library_catalog.dart` ↔ `album_library.dart` / `artist_library.dart` 存在**循环 import**。
  Dart 允许，且这些顶层 final 都是惰性构造（provider 构造不执行闭包），无初始化顺序风险。
- 仍未处理：`mostPlayedAlbumsProvider` 的 build 期双层循环、`_ArtistsRowSection` 的同步
  `existsSync` + 网络预取、未过滤语义不一致、`watchArtistSummaries` 那条低频全表扫。
