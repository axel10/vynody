## 媒体库首页性能审查（只读分析，未改代码）

排查 `lib/pages/library_dashboard_view.dart` 及其数据链路的阻塞点。核心结论：**问题不在单次查询慢，而在「一次 songs 表写入 → 6 路全表重算」的放大器结构，且首页常驻。**

### 关键事实（带位置）

- 首页共订阅 **6 路** 基于 `MetadataDatabase().watchAllSongMetadata()` 的流：
  `albumLibraryProvider`(album_library.dart:11)、`artistLibraryProvider`(artist_library.dart:14)、
  `genreLibraryProvider`(library_overview_providers.dart:39)、`yearLibraryProvider`(:121)、
  `allRatedSongsProvider`(:261)、`timeMachineAlbumsProvider`(:321)。
- **只有 album / artist 加了 `.throttleLeadingAndTrailing(1s)`**（album_library.dart:33、
  artist_library.dart:66）；genre / year / allRated / timeMachine 四路无节流。
  节流实现见 `lib/utils/stream_utils.dart`。
- `watchAllSongMetadata()` 是 drift `customSelect` + `ORDER BY LOWER(path) ASC`
  （metadata_drift_database.dart:818），函数排序走不了索引，每次变更都全表重排；
  `_songFromQueryRow`(:2799) 每行还做 3 次 `IosPathManager.resolveSandboxPath` + `jsonDecode(genres)`。
- **触发源极高频**：`scanner_service.dart:413 updateSongThumbnailPath` → `insertOrUpdateSong` 写 songs 表，
  调用点是 `song_thumbnail.dart:151/164`（每张缩略图生成后回调）。所以「首屏渲染出缩略图」本身就会
  反复捅这个放大链路。（scanner 侧的 notify 有 150ms 节流 + structureRevision 指纹，DB 侧没有。）
- **首页常驻**：dashboard 是 `library_page.dart:229` 的 Navigator 栈底路由，推入二级页后仍在树上；
  MainLayout 的 IndexedStack 也让整个媒体库页常驻。→ 人不在首页时这套成本照付。
- section 用的 `_cachedXxx` 快照（ref.listen + `if (_cached == null)`）**只省了 UI 重建，没省 provider 计算**，
  订阅一直活着。
- 与之相反，`_DashboardHeader` / `_WideQuickAccessBar` / `_PortraitLibraryMenuCard` 是
  `ref.watch(genre/yearLibraryProvider).value?.length` —— StreamProvider 每次 emit 新的 `List` 实例，
  `AsyncData` 判等失败 → 这三处必重建（快捷入口栏重建 9 张卡片）。
- 纯 `Provider`（同步）在 build 阶段做重活：`mostPlayedAlbumsProvider`(:438)、
  `recentlyAddedAlbumsProvider`(:680)、`topRatedAlbumsProvider`(:733)，其中 mostPlayedAlbums 是
  双层循环（所有专辑 × 专辑内所有歌，:476-487），由 section build 里的 `ref.read` 同步触发。
- 循环内低效写法：`library_overview_providers.dart:75` 和 `:154` 用
  `s.path.split(RegExp(r'[/\\]')).last` 逐行新建正则（album_library 用的是 `p.basename`，正确）。
- 同步 IO 在 build 里：`_ArtistsRowSection._prefetchDisplayedArtists` 对 12 个艺术家逐个
  `File(...).existsSync()`；`_DashboardArtistItem.initState` 同样 existsSync + 发起 TheAudioDB 网络请求。
- `_RecentlyPlayedSection` 的 itemBuilder 内 `previewItems.map((e) => e.song).toList()`（:1117 附近）
  每项重建整表，20 项，O(n²) 分配但量级很小。

## 播放页「音频规格信息」时有时无 —— 链路梳理（只读分析，未改代码）

渲染点：`PlaybackAudioInfoLabel`（`lib/widgets/playback/playback_progress_section.dart:304`），
由 `playback_controls.dart:1128 / 1202 / 1255` 三处调用（overlay 竖屏 / 横屏 / 普通竖屏），
位置都在进度条 + 按钮行下方（`audioInfoGap=6` / `audioInfoHeight=18`），受设置项
`showPlaybackAudioInfo` 控制（关掉时整块不渲染）。文本 = `formatAudioSpec(details)`，
按 `FORMAT · 24BIT · 96 kHz · 1411 kbps` 顺序拼，缺项跳过。

数据源 `currentAudioDetailsProvider`（`lib/player/audio/audio_riverpod.dart:290`），
`build()` 里四级优先级：
1. `audioService.getCachedAudioDetails(path, lastModifiedTime:)` 且 `sampleRate > 0` → 秒开
2. `currentMusic.sampleRate != null && > 0` → `MusicFile.toAudioDetails()`
3. `scannerService.metadataMap[path].sampleRate > 0` → 从扫描结果构造
4. 兜底 `buildFastAudioDetails()`：**只按扩展名推 format/codec，其余字段全 0**；
   同时挂 350ms 防抖 → `_loadRefinedDetails()` 走内核 TagLib 精解析并 `state = refined`

**已识别的三个「没」的来源（都还没修）**：
- 走第 4 级时先只有格式名（本地 .flac 等仍能显示 "FLAC"），350ms 后才有完整规格；
  `_loadRefinedDetails` 的 `catch (_) {}` 会静默吞掉失败 → 永远不完整。
- **空结果污染内存缓存**：`audio_service.dart:3151/3166` 与 `audio_riverpod.dart:509`
  都无条件 `setCachedAudioDetails`。一旦写入 `sampleRate == 0` 的条目，
  后续进同一首会「cached 存在但 sampleRate==0」→ 跳过第 1 级 → 落到
  `fastDetails = cached`（这份是**未 refine** 的原始 details）→ 空行。
  只能靠重启或超过 `_maxAudioDetailsCacheSize = 100` 淘汰才恢复。
- **远程曲目（subsonic/jellyfin/webdav/smb）**：`buildMusicFileFromSubsonic`
  (`remote_media_resolver.dart:370`) 只填 title/artist/album/duration，
  **不填 sampleRate/format**；`path` 是 `subsonic://serverId/trackId` 无扩展名，
  只能靠 `name = '$title.$suffix'` 兜底出格式名。
  `getAudioDetails` 只有在 `streamCacheManager.isTrackCached == true` 时才会用
  缓存文件路径解析，在线流会拿虚拟 URI 直接问内核 → 拿不到。
  即「同曲目：已缓存/已下完 → 有；边下边播 → 只有格式名或没有」。
  注：Subsonic/Jellyfin 的 trackJson 里其实带 `samplingRate` / `bitRate` /
  `channelCount`，当前代码完全没读，这是可以直接补的优化点。

## 播放页「只显示格式名」定因并修复（真因：riverpod 重建吞掉防抖定时器）

用户提供 `vynody_1792190825122.log`（9563 行），三首歌对照即可定性：

| 歌曲 | 关键日志 | 结果 |
|---|---|---|
| All falls down | `src=fast` → 53ms 后 `refine=engineReturned sr=44100 br=320000`（无 `refineTimer fired`） | 正常（走了 `loadRefinedImmediately`，它先 cancel 定时器再直接解析） |
| I Can't Let U Go | `src=fast` → 418ms 后 `refineTimer fired` → 成功 | 正常 |
| **Pop Ya Collar** | `src=fast(fromCache=false) fmt=mp3|sr=0` 之后再无任何 `refine=` 行 | **定时器被取消，精解析从未执行** |

**真因**：riverpod 的 `ref.onDispose` 在 provider **重建**时也会触发
（`riverpod-3.4.3/lib/src/core/element.dart:616 _performRebuild()` 第一件事就是 `runOnDispose()`；
`Ref.onDispose` 文档原文 "This includes: when the provider will rebuild"）。
而 `CurrentAudioDetailsNotifier.build()` 里 `ref.onDispose(() => _debounceTimer?.cancel())`，
再加上「同曲目早退」分支直接 `return state` 不重新安排定时器 ——
**只要 350ms 窗口内发生过一次 rebuild，精解析就永远不会跑**。

为什么这个窗口经常被击中：`MusicFile.==`（`lib/models/music_file.dart:117`）把 `thumbnailPath` /
`artworkPath` / `durationMillis` 都纳入比较，`themeColorsBlob` / `waveformBlob` / `artworkBytes`
用 `identical` 比较；切歌后封面解码、主题色提取、波形生成（日志里 `_updateCurrentMetadata`
`Background processing (Thumbnail/Colors/Waveform)`、`WaveformRead #8 SUCCESS`）都会回写这些字段
→ `audioCurrentMusicProvider` 发新值 → 本 notifier 重建 → 定时器被 onDispose 取消。
所以表现为「有时有有时没有」：窗口内没被重建击中就正常，被击中就只剩 `MP3`。
（`_updateCurrentMetadata decodeEmbeddedArtwork/artwork hydrate` 在 Pop Ya Collar 上耗时 704ms，
正好横跨 35.664 → 36.014 的窗口。）

**修复**（`lib/player/audio/audio_riverpod.dart`）：
- 抽出幂等的 `_armRefine(music)`：`_refineTriedPath == path` 或定时器在跑则直接返回。
- 「同曲目早退」分支补挂 `_armRefine(currentMusic)` —— 这是本次的关键修复点。
- 截止时刻 `_refineDeadline` 锚在**切歌**而非最后一次 build；窗口被反复 rebuild 耗尽时
  （`remaining <= 0`）直接同步发起精解析，避免被无限推迟（打印 `refineTimer expiredRunNow`）。
- `_loadRefinedDetails()` 开头记 `_refineTriedPath`，防止补挂导致重复走 TagLib FFI；
  切歌 / `currentMusic == null` 时重置 `_refineDeadline` 与 `_refineTriedPath`。
- `loadRefinedImmediately()` 里补 `_debounceTimer = null`。

**诊断日志已按用户要求全部清除**：删掉 `lib/player/audio/audio_riverpod.dart` 里所有 `[AudioSpec]`
debugPrint（含 onDispose 里的 `cancelledByRebuildOrDispose`、`refineTimer fired`/`expiredRunNow`、

## 流派图标（assets/icons/genre）轮廓重绘，15 个

## 流派裂成两个同名条目（J-Pop / JPop）

用户报「流派里怎么两个 j-pop」。查库确认 `songs.genres` 里 `["J-Pop"]` 11 首、
`["JPop"]` 1 首（`君が好きだと叫びたい1` / BAAD，标签无连字符）。

根因：`normalizeGenreKey()` 只收敛大小写与标点，`-` 被当分隔符换成空格，于是
`J-Pop → j pop`、`JPop → jpop`，两个聚合键不同就裂成两组；而
`pickGenreDisplayName()` 的 `_acronymDisplays` 把两条都美化成 `J-Pop`，
列表里看起来就是同一流派重复两次。封面都是 j-pop 图（`_exactAssetAliases`
有独立条目兜住），更像重复。

修法：`genre_naming.dart` 新增 `_genreKeyEquivalents`（键 = 归一化结果去空格，
值为规范键），在 `normalizeGenreKey()` 末尾查表：jpop→j pop、kpop→k pop、
hiphop→hip hop、lofi→lo fi、rnb/rb/randb→r and b。收录口径只限
「连字符/空格/连写」这一维，不做同义词合并（Rap→Hip-Hop 归资源键层管）。

连带清理 `_exactAssetAliases` 里因收敛而不可达的键（hiphop/rnb/r b/jpop/kpop/lofi）。
**子串规则 `_substringAssetRules` 里的 jpop/kpop/lofi 必须保留** —— 长尾写法
（`kpop dance`）compact 后不在等价表里，仍靠子串命中。
`_acronymDisplays` 也不能动，它吃的是 `raw.toLowerCase()` 而非归一化键。

验证：真实库 21 种写法跑一遍，`j pop` 组合并成 12 首。新增两条单测。
