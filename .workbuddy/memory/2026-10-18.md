## 洞察页「歌曲 / 专辑」切换卡顿 + 闪屏：已完成成因定位（未改动代码）

现象：最近添加 / 最近播放 / 最多播放 三页里点「专辑」pill，整页卡一下并闪一下。

定位结果（三页同构，`*_tab.dart` 分支写法一致）：

1. **闪 = 整棵列表被销毁重建**。`RecentlyAddedTab.build` 在 `isAlbums` 时直接 return
   `LibraryRankedAlbumList`，否则 return `LibraryRankedSongList`。根节点 runtimeType 变化，
   Element 无法复用 → `ScrollController`、搜索词、滚动位置全部丢失，新列表从顶部重新布局。
   两个列表的 header / 滚动容器是各自复制的一份实现，切换瞬间页头高度也随之跳变。

2. **卡 = 专辑列表一次性构建全部行**。`library_ranked_album_list.dart` 用
   `SliverToBoxAdapter > ListView.separated(shrinkWrap: true, physics: NeverScrollable)`，
   shrinkWrap 必须测量全部 child → 最多 500 行（`watchRecentlyAdded` 默认 limit=500）一帧全建；
   对照 `library_ranked_song_list.dart` 用的是 `SliverFixedExtentList.builder` 懒构建。

3. 每行附带额外同步开销：`itemBuilder` 里 `entry.toAlbumSummary()`（firstWhere + fold）无缓存；
   `build` 里 `playAllSongs = filteredItems.expand((e) => e.songs).toList()` 把 500 张专辑的
   全部曲目展开成一个大 List；`SongThumbnail.initState` 对每行做 `File(...).existsSync()` 同步
   IO（`song_thumbnail.dart:112`），500 行 ≈ 500 次同步 syscall。

4. 首次切到专辑还会执行 `_aggregateInsightAlbums`（`library_overview_providers.dart:574`）：
   对全量专辑建索引（title/artist 各两次 trim+toLowerCase），再对 ≤500 首分桶、排序，全在
   UI isolate 同步完成。

5. **隐患（会单独触发整页闪）**：`_combineInsightAlbums` 用 `isLoading` 判断并返回
   `const AsyncValue.loading()`，会把旧值丢掉。播放一首歌 → 写 songs 表 → catalog 推新快照 →
   `albumLibraryProvider` 进入 reload → 专辑视图整页变加载圈再回来。同样的问题在
   `recentlyAddedAlbumsProvider` / `topRatedAlbumsProvider` / `mostPlayedAlbumsProvider`。
   这与 MEMORY 里「曲库派生页禁把 reload 当首次加载」是同一类错误，四个 provider 均未遵守。

修复方向（待用户确认，尚未动手）：
- P0 专辑列表改 `SliverFixedExtentList` / `SliverList.builder` 懒构建。
- P0 `_combineInsightAlbums` 改成 `hasValue` 判定，reload 时沿用旧值。
- P1 两列表抽公共 shell，切歌/切专辑只换 sliver，保留滚动与搜索状态。
- P1 `toAlbumSummary()` 与 `playAllSongs` 移出 build / itemBuilder（provider 侧预算或缓存）。

## 媒体库路由结构诊断（未改代码）

用户反馈：进专辑详情 → Rail 切到艺术家 → 切回专辑，详情页丢失；切走时封面多出一段 hero 飞行动画。

9 个子分类不是路由，是 `library_sub_host` 里的一个 `IndexedStack`（`:439`），三级页压在同一条 Navigator 上，没有 tab 归属。

成因：
1. Rail 子项 → `libraryActiveTabIndexProvider.set(n)`（`main_layout.dart:1442`）→ `library_page.dart:207` 的 listener 直接 `popUntil(library_sub_host)`。切 tab 被翻译成出栈，所以详情必丢。

待定方案：
- A 只治动画（切 tab 前关 hero + 无动画出栈），仍丢详情；
- B 每 tab 一个 Navigator（三级页归属各自 tab，切 tab 天然保留）；
- C 记 `(tabIndex, albumId)` 事后重建（补丁）。

用户倾向讨论 B 是否「最清晰易维护」。已说明 B 的前提：抽 `LibraryTabNavigator` 外壳、返回键集中分发、`dismissSubPages` 改为退所有 tab、洞察页筛选复位点要从「宿主页 dispose」换掉（保留栈后 dispose 不再发生）。统计：9 个 tab 里 7 个会 push 三级页（专辑/艺术家/流派/年份 + 三个洞察 tab 的专辑详情）。

## 修复：目录页首次播放某首歌时该行封面闪白

链路（只发生在「首次播放」）：`AudioService._updateCurrentMetadata` → `_needsPlaybackMetadataRefresh()` 为真（标题/歌手/专辑无意义或时长缺失，即无标签文件）时 `loadMetadataForPlayback(forceRefresh: true)` → `_scannerService.updateMetadataForPath(metadata, artworkBytes: bytes)`：

## 优化：播放不再把封面字节写进目录树（内存常驻）

`ScannerService` → `ScannerMetadataStore` 的 `folder.files` 是会话级常驻对象（重扫才由 `scanner_tree_builder` 重建），而 `updateMetadataForPath(metadata, artworkBytes: ...)` 会把 `_updateMusicFileInFolder` 里的 `MusicFile.artworkBytes` 写成整张封面 JPEG（100KB~1MB，不经 `ImageCache` 计数）。播放链路里每首「播过一次」的歌都会走两次写入：

1. `_resolveMetadataForPlayback`（无标签/时长缺失时）→ `updateMetadataForPath(metadata, artworkBytes: artworkBytes)`；
2. `saveCurrentSongThemeColors`（首次播放且库里还没主题色时）→ `updateMetadataForPath(updatedMetadata, artworkBytes: updatedSong.artworkBytes)`。

结果：逐首播一遍的无标签目录，几十到几百 MB 常驻，GC 无法回收（树一直强引用）。

改：两处都改成 `updateMetadataForPath(metadata)`，只写 `thumbnailPath` / `artworkPath` / 主题色等路径类字段。播放侧不受影响——`_songFromMetadata` 已把字节放进 `updatedSong`，经 `_replaceQueueSongsByPath` 进 `currentMusic` 与队列；`queue_background_processor` 本来就把队列里非当前 ±1 的 `artworkBytes` 清空。列表行改用缩略图文件（56px 只需缩略图），顺带消除了「文件源 → 内存源」的切换，首次播放那次闪白也更不会出现。

当时未动（下一条已收紧，改由 store 层兜住）：`song_tag_edit_dialog` / `song_context_menu_utils` / `playback_page` 的「用户主动改标签/存回文件」路径仍会把字节写回树（单曲、用户触发，需要树立刻反映新封面）。`test/player` 338 例、`test/pages` 49 例、`test/widgets` 207 例全过。

## 收紧：目录树彻底不放二进制列（硬性规定）

上一条只堵了播放链路两处调用点，仍有三类漏法：`scanner_tree_builder` 建树时把 `themeColorsBlob` / `waveformBlob` 从 DB 抄进 `MusicFile`（重扫后全库波形 blob 常驻）；`_updateMusicFileInFolder` 仍接受并写入 `artworkBytes`；改标签路径会再塞封面。

改为**结构性约束**，不靠调用方自觉：

1. `scanner_tree_builder.dart` 三个工厂（`musicFileFromSongMetadata` / `_musicFileFromPath` / `musicFileFromAndroidEntry`）不再透传 `themeColorsBlob` / `waveformBlob`。
2. `ScannerMetadataStore._updateMusicFileInFolder` 的 copyWith 里三项直接写 `null`，`artworkBytes` 参数退化成「清空封面」哨兵（空数组 → 清空 `thumbnailPath`/`artworkPath`/宽高）。调用方传什么字节都不会进树。
3. 数据源统一 SQLite：`TrackArtworkThemeService.getTrackArtworkTheme`（DB 命中 `hasCompleteData` 直接返回）、`WaveformService.streamWaveform`（先查 `songMetadata.waveformBlob`）。缺就生成、生成后写回 DB。播放态（`currentMusic` / 队列）自己持有，`queue_background_processor` 清非当前 ±1。
4. 页面级持有者销毁即释放：`playback_page.dispose` 里 `_pendingArtworkBytes = null`（原来只清了 `_fileArtworkBytesCache`）；`cover_carousel` 的 `_CoverItemState.dispose` 清 `_artworkBytes` / `_artworkFilePath` / `_remoteArtworkUrl`（原来只取消 listener 和定时器）。

新增回归 `test/player/scanner_tree_blob_free_test.dart`（3 例：更新路径不写三类 blob 但保留引用字段、空字节哨兵仍能清封面、建树工厂丢弃三类 blob）。`test/player` 341 例、`test/pages` 49 例、`test/widgets` 207 例全过；`flutter analyze lib` 仍是 118 条既有 warning/info。

遗留观察（未改）：`AudioService._artworkCache` 按「200 条」封顶而不是按字节，200 张原图最坏可到 100MB 量级，是下一个值得处理的内存点。

## 修复：收起态切页后下滑「先展开再收起」

现象：Dock 收起时切到别的主页面，再往下滑，会先展开一下再收回。

两处成因：
1. `main_layout.dart` `_selectTab()` 无条件 `setCollapsed(false)`，把「收起由滚动派生」的前提破坏掉；展开走 `AnimatedContainer` 300ms，而滚轮一格 `scrollDelta` 常 ≥72px 的收起阈值，动画刚起步就被反向。
2. `FloatingDockScrollHelper` 对 `pixels <= 20` 的**每一帧**都无条件展开 —— 新页面通常停在顶部，收起态一往下滑就先被这一步展开，滚过 20 再累计 72 收起。这条才是主因。

修：
- `_selectTab` 改为 `_dockScrollHelper.reset(ref)`（清累计 + 半收起进度 + `_lastPixels`），不再碰收起态。收起状态跨页面延续。
- helper 新增 `_lastPixels`，顶部缓冲区展开改成边沿触发（`previousPixels > 20 && pixels <= 20`）；底部仍无条件展开（到底后无法再下滑，不受影响）。
- 顺带修掉跨页累计：以前 A 页滚 60（未达 72）+ 切页 + B 页滚 15 = 收起，`setCollapsed` 只 reset progress 不清 helper 内部字段。

回归：新增 `test/pages/floating_dock_scroll_helper_test.dart` 三例（顶部下滑不展开 / 从下方滚回顶部仍展开 / 切页后累计归零）。`floating_dock_bottom_bar_test` 既有 12 例全过（其中 "expands when scrolling near bottom" 是第一次改动的反例，故保住了底部无条件展开）。`test/pages/main_layout_rail_test` + `back_press_navigation_test` 通过；analyze 只剩既有 2 条（`_currentBaseTabIndex` 只写不读为该文件既有问题）。

遗留：`_lastPixels` 不区分 Scrollable，同页嵌套垂直列表之间可能误判边沿（与既有的 `_accumulatedDownScroll` 跨列表共享同类）。

## 真正根因（run.log 打点定位）：边沿判断跨了 Scrollable

用户反馈上一版修复无效，加 `[DockTrace]` 打点（helper 实例号/序号、pixels/prev/dy/collapsed/depth/通知类型、setCollapsed 带 reason、dock.build 渲染态）后 run.log 一锤定音：

时间线：目录页（max=1863）滚到 px=107 收起 → 用户**点进子目录**（页内跳转，`setNavigationState`，不经过 `_selectTab`，上一版的 reset 没跑到）→ 新列表（max=603）第一条通知 `px=0.0 prev=107.0` → `107>20 && 0<=20` 被误判成「从下方滚回顶部」→ `setCollapsed(false, reason=top-buffer-edge)` 展开 → 下滑满 72 又收起。

修：`FloatingDockScrollHelper` 新增 `_lastScrollableContext`（用 `notification.context`，即 Scrollable 的 notificationContext，同一 Scrollable 稳定）；`previousPixels = identical(context, _lastScrollableContext) ? _lastPixels : null` —— 边沿只在同一列表内成立，换列表一律视为首次通知。`reset()` 同时清 `_lastScrollableContext`。

回归：`floating_dock_scroll_helper_test.dart` 新增「跨列表 pixels 跳变不触发展开 + 同列表滚回顶部仍展开」用例（模拟两个不同 context）。16 例全过；analyze 改动文件仅剩既有 2 条。

诊断日志保留，统一受 `FloatingDockScrollHelper.traceEnabled`（static，默认 true）控制：helper 打点、notifier 的 build/setCollapsed、`_selectTab`、dock.build 渲染态。问题确认修复后应整体拆除或把默认值改 false。教训：**边沿类判定绝不能跨 Scrollable 比较 pixels**——`max` 值突变（1863→603）就是换列表的信号。

## 修复：启动恢复播放状态时播放页背景先闪队列第一首封面

现象：冷启动恢复播放状态后，播放页背景封面先显示队列第一首的歌，再跳回当前歌。

## 逐字歌词回跳风险审查（只分析未改码）

结论：常规播放/seek/暂停路径防护齐全；残留 3 个边缘场景。

已有防护：`WordWordLyricsWidget`（`lyrics_panel_views.dart:1041`）用「基线+墙钟插值」渲染，内核 tick 只做校准；`ref.listen(audioPositionProvider)` 的 300ms 阈值吸收 <300ms 抖动（`lyrics_panel_views.dart:1213`）；行级 `_activeLineIndex` 二分查找单调 + `_overrideActiveIndex` 锚定 seek 目标行（`lyrics_panel.dart:1639-1658`，容忍 ±400ms/2s 的 seek 落点偏早）；seek 期间 `_isSeeking` 把 position 钉在目标值（`audio_service.dart:1608-1625`）。

残留风险：
1. **变速不重建基线（明确 bug）**：`_calculateCurrentPosition`（:1084）把基线以来全部 elapsed 乘新速度，`didUpdateWidget`/`ref.listen` 均未监听 `playbackSpeed` 变化。2.0x→1.0x 瞬间向后跳「elapsed×速度差」，靠下一个内核 tick（>300ms）才拉回，播放中约一个 tick 内可见闪跳；暂停时保持错误直到恢复播放。修法：speed 变化时以当前计算位置为新基线 `_syncBaseline`。
2. **墙钟 vs 音频钟漂移的硬校正**：漂移累计 >300ms 时一次 tick 硬拉回 ≤300ms，每几分钟一次的小幅瞬时回跳。根治需渐进追赶或内核侧音频钟插值。
3. **后台暂停/恢复过冲**：pause 分支把整个后台时长计入 `_pausedElapsed`（音频实际中途已停），恢复瞬间先冲过头再被 listen 拉回，一次先冲后回的闪动。

## Android release 崩 SharedPreferencesApiRegistrar.getAll（17:42）

现象：`flutter run --release` 启动即 `NoSuchMethodError: no non-static method "...SharedPreferencesApiRegistrar;.getAll(...Lkotlin/coroutines/Continuation;)..."`。

根因链（已用产物验证，非猜测）：
1. Flutter 3.44 的 `FlutterPlugin.kt:217` 在 release **默认** `isMinifyEnabled = true`（`shouldShrinkResources` 默认 true，可用 gradle 属性 `shrink=false` 关闭），并自动加载 `android/app/proguard-rules.pro`（存在才加载）。
2. `shared_preferences_android` 2.5.0 起改用 **Pigeon JNI**，Dart 侧按原始 JVM 签名 `GetMethodID` 反射调用；Kotlin suspend 方法的最后参数是 `kotlin.coroutines.Continuation`。
3. R8 把这个接口重命名（旧 mapping：`residualsignature "(Ljava/lang/String;Ljava/util/List;LJ3/d;)Ljava/lang/Object;"`）→ JNI 查不到。
4. 类名/方法名本身没被改（`@Keep` + ProGuard 保留），只有**参数类型名**被改，所以报的是 NoSuchMethod 而非 ClassNotFound。debug/profile 不混淆，故只在 release 出现。

修复：新增 `android/app/proguard-rules.pro`（Flutter 自动加载）：
`-keepnames class io.flutter.plugins.**`、`-keepnames class dev.flutter.pigeon.**`、`-keepnames class kotlin.coroutines.**`。
验证：重建后 mapping 无 residualsignature；`dexdump` 确认 `getAll` proto = `(Ljava/lang/String;Ljava/util/List;Lkotlin/coroutines/Continuation;)Ljava/lang/Object;`。

诊断手法（可复用）：`build/app/outputs/mapping/release/mapping.txt` 看 `residualsignature`；`dexdump <dex> | rg -A60 "Class descriptor.*<类名>"` 看真实 proto。注意 `build/app/outputs/flutter-apk/app-release.apk` 全 ABI 约 130MB，`flutter run --release` 只打单 ABI 约 57MB，别拿体积对比当异常。

### 上一条的补丁不够 —— 第二环：kotlin.Result

第一版规则只 `-keepnames class kotlin.coroutines.**`，`getAll` 的 proto 修好了，但随即抛
`ClassNotFoundException: Didn't find class "kotlin/Result"`。mapping 显示 `kotlin.Result -> E3.e`：
Pigeon ProxyApi 的异步返回值包在 `kotlin.Result` 里，R8 把它改名了。

最终规则（`android/app/proguard-rules.pro`）：
```
-keepnames class io.flutter.plugins.** { *; }
-keepnames class dev.flutter.pigeon.** { *; }
-keepnames class kotlin.** { *; }     # 收口：Result/Unit/coroutines 全在 kotlin 包下
```

实机验证（adb，Redmi Turbo 4 Pro / arm64-v8a）：`flutter build apk --release --target-platform android-arm64`
→ 59.5MB → `adb install -r` → `am start` → logcat 无 NoSuchMethod/ClassNotFound/PlatformException，进程存活，正常进首次启动的目录选择流程。

结论：**不用降级 shared_preferences_android**。若以后别的 JNI 化插件再冒同类异常，优先级：补对应包的 keepnames > `android/gradle.properties` 加 `shrink=false` 关 R8 > 降级插件。

## 目录排序小改落地：默认音轨号 + 覆盖高亮

- 默认排序 `filename` → `trackNumber`：只在 `ScannerService` 加 `_defaultSortCriteria`，且只在 prefs 里**没有**该 key 时生效（显式存过 filename 的老用户不变）。`SortCriteriaX.fromStorageValue` 的兜底仍是 filename——WebDAV 浏览共用同一枚举，不能改。
- 排序是**就地 `sort`**，`_computeStructureFingerprint` 只看对象 identity 与歌曲总数，感知不到顺序变化。新增 `_markSortOrderChanged()`（`_structureRevision++` + `_rootFoldersView = null`），在 `_sortAndNotify()` 收尾与 `setFolderSortLocalized(开启)` 里各调一次；否则改完排序列表停在旧顺序、顶栏高亮也不刷新。
- 顶栏排序按钮拆两个状态：`isSortActive`（根目录拖拽模式，保留 `primaryContainer` 底色 + 对勾）、`isSortHighlighted`（当前目录有覆盖，**只染图标色，不铺底色**）。最初把后者也接到 `isSelected` 上，导致普通目录出现整块主题色，已按用户反馈改回。
- 「仅此目录」开关打开即物化覆盖（值等于当前生效值，画面不变）；关闭即删覆盖回全局。`removeRootPaths` 同步清理对应键。
- 新增测试：`test/player/scanner_sorting_test.dart`（比较器：空值恒在末尾、降序不翻转缺失项）、`test/player/folder_sort_override_test.dart`（覆盖增删/隔离/默认值）、`test/widgets/folder_sort_sheet_test.dart`（浮层交互）。注意 `dart format` 会顺带重排整份未格式化文件，只能手改，别对整文件跑。

## 目录排序浮层改为「确定才生效」

- 浮层内所有选择（排序方式 / 顺序 / 仅此目录开关）只改本地 `setState` 状态，底部按钮从单个「完成」换成「取消 / 确定」；`确定` → `ScannerService.applySortSettings(...)` 后 pop，其余关闭方式（关闭按钮 / 点遮罩 / 下拉）等同取消。
- `applySortSettings` 是唯一收口：localized 时写该目录覆盖，否则删覆盖 + 写全局，最后只 `_sortAndNotify` 一次。原来的 `setGlobalSort` / `setFolderSort` / `setFolderSortLocalized` 现在只剩测试在用（保留，语义仍成立）。
- 关掉「仅此目录」时把选项同步成当前全局值（因为确定后此目录就跟随全局），避免把覆盖值顺手推给全局。
- 测试改成用真实路由打开浮层（`showFolderSortSheet` + 按钮触发），否则 `Navigator.pop()` 落在唯一路由上；浮层可能超高，点按钮前要 `ensureVisible`。
