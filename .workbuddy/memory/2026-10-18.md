## 洞察页「歌曲 / 专辑」切换卡顿 + 闪屏：已完成成因定位（未改动代码）

现象：最近添加 / 最近播放 / 最多播放 三页里点「专辑」pill，整页卡一下并闪一下。

定位结果（三页同构，`*_tab.dart` 分支写法一致）：

1. **闪 = 整棵列表被销毁重建**。`RecentlyAddedTab.build` 在 `isAlbums` 时直接 return
   `LibraryRankedAlbumList`，否则 return `LibraryRankedSongList`。根节点 runtimeType 变化，
   Element 无法复用 → `ScrollController`、搜索词、滚动位置全部丢失，新列表从顶部重新布局。
   两个列表的 header / 滚动容器是各自复制的一份实现，切换瞬间页头高度也随之跳变。

2. **卡 = 专辑列表一次性构建全部行**。`library_ranked_album_list.dart` 用
   `SliverToBoxAdapter > ListView.separated(shrinkWrap: true, physics: NeverScrollable)`，
   shrinkWrap 必须测量全部 child → 最多 500 行（`watchRecentlyAdded` 默认 limit=500）一帧全建；
   对照 `library_ranked_song_list.dart` 用的是 `SliverFixedExtentList.builder` 懒构建。

3. 每行附带额外同步开销：`itemBuilder` 里 `entry.toAlbumSummary()`（firstWhere + fold）无缓存；
   `build` 里 `playAllSongs = filteredItems.expand((e) => e.songs).toList()` 把 500 张专辑的
   全部曲目展开成一个大 List；`SongThumbnail.initState` 对每行做 `File(...).existsSync()` 同步
   IO（`song_thumbnail.dart:112`），500 行 ≈ 500 次同步 syscall。

4. 首次切到专辑还会执行 `_aggregateInsightAlbums`（`library_overview_providers.dart:574`）：
   对全量专辑建索引（title/artist 各两次 trim+toLowerCase），再对 ≤500 首分桶、排序，全在
   UI isolate 同步完成。

5. **隐患（会单独触发整页闪）**：`_combineInsightAlbums` 用 `isLoading` 判断并返回
   `const AsyncValue.loading()`，会把旧值丢掉。播放一首歌 → 写 songs 表 → catalog 推新快照 →
   `albumLibraryProvider` 进入 reload → 专辑视图整页变加载圈再回来。同样的问题在
   `recentlyAddedAlbumsProvider` / `topRatedAlbumsProvider` / `mostPlayedAlbumsProvider`。
   这与 MEMORY 里「曲库派生页禁把 reload 当首次加载」是同一类错误，四个 provider 均未遵守。

修复方向（待用户确认，尚未动手）：
- P0 专辑列表改 `SliverFixedExtentList` / `SliverList.builder` 懒构建。
- P0 `_combineInsightAlbums` 改成 `hasValue` 判定，reload 时沿用旧值。
- P1 两列表抽公共 shell，切歌/切专辑只换 sliver，保留滚动与搜索状态。
- P1 `toAlbumSummary()` 与 `playAllSongs` 移出 build / itemBuilder（provider 侧预算或缓存）。

## 媒体库路由结构诊断（未改代码）

用户反馈：进专辑详情 → Rail 切到艺术家 → 切回专辑，详情页丢失；切走时封面多出一段 hero 飞行动画。

9 个子分类不是路由，是 `library_sub_host` 里的一个 `IndexedStack`（`:439`），三级页压在同一条 Navigator 上，没有 tab 归属。

成因：
1. Rail 子项 → `libraryActiveTabIndexProvider.set(n)`（`main_layout.dart:1442`）→ `library_page.dart:207` 的 listener 直接 `popUntil(library_sub_host)`。切 tab 被翻译成出栈，所以详情必丢。

待定方案：
- A 只治动画（切 tab 前关 hero + 无动画出栈），仍丢详情；
- B 每 tab 一个 Navigator（三级页归属各自 tab，切 tab 天然保留）；
- C 记 `(tabIndex, albumId)` 事后重建（补丁）。

用户倾向讨论 B 是否「最清晰易维护」。已说明 B 的前提：抽 `LibraryTabNavigator` 外壳、返回键集中分发、`dismissSubPages` 改为退所有 tab、洞察页筛选复位点要从「宿主页 dispose」换掉（保留栈后 dispose 不再发生）。统计：9 个 tab 里 7 个会 push 三级页（专辑/艺术家/流派/年份 + 三个洞察 tab 的专辑详情）。

## 修复：目录页首次播放某首歌时该行封面闪白

链路（只发生在「首次播放」）：`AudioService._updateCurrentMetadata` → `_needsPlaybackMetadataRefresh()` 为真（标题/歌手/专辑无意义或时长缺失，即无标签文件）时 `loadMetadataForPlayback(forceRefresh: true)` → `_scannerService.updateMetadataForPath(metadata, artworkBytes: bytes)`：

## 优化：播放不再把封面字节写进目录树（内存常驻）

`ScannerService` → `ScannerMetadataStore` 的 `folder.files` 是会话级常驻对象（重扫才由 `scanner_tree_builder` 重建），而 `updateMetadataForPath(metadata, artworkBytes: ...)` 会把 `_updateMusicFileInFolder` 里的 `MusicFile.artworkBytes` 写成整张封面 JPEG（100KB~1MB，不经 `ImageCache` 计数）。播放链路里每首「播过一次」的歌都会走两次写入：

1. `_resolveMetadataForPlayback`（无标签/时长缺失时）→ `updateMetadataForPath(metadata, artworkBytes: artworkBytes)`；
2. `saveCurrentSongThemeColors`（首次播放且库里还没主题色时）→ `updateMetadataForPath(updatedMetadata, artworkBytes: updatedSong.artworkBytes)`。

结果：逐首播一遍的无标签目录，几十到几百 MB 常驻，GC 无法回收（树一直强引用）。

改：两处都改成 `updateMetadataForPath(metadata)`，只写 `thumbnailPath` / `artworkPath` / 主题色等路径类字段。播放侧不受影响——`_songFromMetadata` 已把字节放进 `updatedSong`，经 `_replaceQueueSongsByPath` 进 `currentMusic` 与队列；`queue_background_processor` 本来就把队列里非当前 ±1 的 `artworkBytes` 清空。列表行改用缩略图文件（56px 只需缩略图），顺带消除了「文件源 → 内存源」的切换，首次播放那次闪白也更不会出现。

当时未动（下一条已收紧，改由 store 层兜住）：`song_tag_edit_dialog` / `song_context_menu_utils` / `playback_page` 的「用户主动改标签/存回文件」路径仍会把字节写回树（单曲、用户触发，需要树立刻反映新封面）。`test/player` 338 例、`test/pages` 49 例、`test/widgets` 207 例全过。

## 收紧：目录树彻底不放二进制列（硬性规定）

上一条只堵了播放链路两处调用点，仍有三类漏法：`scanner_tree_builder` 建树时把 `themeColorsBlob` / `waveformBlob` 从 DB 抄进 `MusicFile`（重扫后全库波形 blob 常驻）；`_updateMusicFileInFolder` 仍接受并写入 `artworkBytes`；改标签路径会再塞封面。

改为**结构性约束**，不靠调用方自觉：

1. `scanner_tree_builder.dart` 三个工厂（`musicFileFromSongMetadata` / `_musicFileFromPath` / `musicFileFromAndroidEntry`）不再透传 `themeColorsBlob` / `waveformBlob`。
2. `ScannerMetadataStore._updateMusicFileInFolder` 的 copyWith 里三项直接写 `null`，`artworkBytes` 参数退化成「清空封面」哨兵（空数组 → 清空 `thumbnailPath`/`artworkPath`/宽高）。调用方传什么字节都不会进树。
3. 数据源统一 SQLite：`TrackArtworkThemeService.getTrackArtworkTheme`（DB 命中 `hasCompleteData` 直接返回）、`WaveformService.streamWaveform`（先查 `songMetadata.waveformBlob`）。缺就生成、生成后写回 DB。播放态（`currentMusic` / 队列）自己持有，`queue_background_processor` 清非当前 ±1。
4. 页面级持有者销毁即释放：`playback_page.dispose` 里 `_pendingArtworkBytes = null`（原来只清了 `_fileArtworkBytesCache`）；`cover_carousel` 的 `_CoverItemState.dispose` 清 `_artworkBytes` / `_artworkFilePath` / `_remoteArtworkUrl`（原来只取消 listener 和定时器）。

新增回归 `test/player/scanner_tree_blob_free_test.dart`（3 例：更新路径不写三类 blob 但保留引用字段、空字节哨兵仍能清封面、建树工厂丢弃三类 blob）。`test/player` 341 例、`test/pages` 49 例、`test/widgets` 207 例全过；`flutter analyze lib` 仍是 118 条既有 warning/info。

遗留观察（未改）：`AudioService._artworkCache` 按「200 条」封顶而不是按字节，200 张原图最坏可到 100MB 量级，是下一个值得处理的内存点。

## 修复：三级详情页的顶栏被宿主顶栏盖住（返回直接回媒体库首页）

现象：专辑详情 → 切目录页 → 回媒体库，仍在专辑详情；点左上角返回直接回媒体库首页。

成因：per-tab Navigator 之后，详情页落在宿主 `IndexedStack`（body）里，而宿主 `AppTopNavBar` 是宿主 `Stack` 的后一个 child，位置完全重合、盖在上面。宿主顶栏没传 `onBack`，`AppTopNavBar` 退化成 `Navigator.of(context).maybePop()` —— 在宿主 context 里弹的是 `library_sub_host`。所以用户点到的根本不是详情页的返回，标题也一直是分类名。

修复：
1. `LibraryTabNavigator` 新增 `_TabRouteStackObserver`（只数非根路由，不用 `canPop()` 避免 pop 中间态）+ `onHasChildRouteChanged`；初始根路由的 didPush 直接早退，规避 build 中 setState。
2. `_LibrarySubHostPageState` 新增 `_tabsWithChildRoutes`，`hideTopNavBar = tabHasChildRoute || (isLandscape && is3DViewActive)`；让位时 duration 用 `Duration.zero`（详情顶栏本来就在同一位置，淡出只会让两个标题交叠）。
3. 宿主顶栏加 `ValueKey('library_subhost_top_bar')` 供测试定位。

回归：`library_page_state_lifecycle_test.dart` 末例（查外层 `AnimatedOpacity.opacity` 1→0→1 + 点详情页自己的返回图标只退详情）。注意 `find.ancestor(...AnimatedOpacity)` 最近的那个是 `AutoHideHeader` 内部的，要 `.at(1)`。

验证：`test/pages` 50、`test/widgets` 207 全过；`flutter analyze lib` 无新增（仍 118，均为既有）。

同类风险备忘：详情页（含 `DetailPageShell`）的 ScrollNotification 现在会冒泡穿到宿主 `AutoHideHeaderScope`（以前详情是独立路由，不会）。表现为「在详情页下滑 → 返回后根页面顶栏也处于收起态」，下次滚动即恢复，暂未处理。
