## 播放页波形进度条性能审计（只读，未改代码）

链路：`PlaybackHeroCard` → `PlaybackControls` → `PlaybackProgressSection`（progress/position/duration/isPlaying 各 watch 一次，约 8Hz 重建）→ `WaveformProgressBar`。

结论：架构选型正确。Ticker(60fps 本地插值) → `ValueNotifier<double>` → `CustomPainter(repaint: notifier)`，进度推进零 setState；`RepaintBoundary` 把重绘限制在波形层；滚动模式按可见区间窗口化只画屏内柱子；暂停/最小化/切歌过渡/后台直接 stop ticker；波形 Float32 BLOB + `MusicFile.waveform` 8 条 LRU 缓存，点数 20~200（默认 100）。

剩余瓶颈（按收益排）：
1. `waveform_progress_bar.dart` `MouseRegion.onHover` 每指针事件 setState（桌面 100~1000Hz），只是为画 2px 游标线 → 应换 ValueNotifier/ValueListenableBuilder；`onExit` 也缺「已是 null 就不重建」判断。
2. 父级 8Hz 重建整棵波形子树（LayoutBuilder + 8 个手势闭包 + didUpdateWidget 的 listEquals）→ 时间文本可拆独立 Consumer。
3. `paint()` 每帧新建 2 个 Path + 2 个 Paint + N 个 RRect；非滚动模式几何不变，可缓存 `Picture`，用 `clipRect + drawPicture` 取代「分界柱单独裁剪」那套逻辑。
4. `_updateAnimatedWaveform` 每帧 `new CurvedAnimation` + 新 List（400ms × 60fps）。
5. `shouldRepaint` 里的 `progress` 比较永远相等（RepaintBoundary 实际由 `repaint:` notifier 驱动），是误导性死代码。
6. 高刷屏 Ticker 不封顶（120/144Hz 全速跑）。

引擎侧：`AudioService._notifyIfNeeded()` 节流 120ms / offset≥120ms 才 notify，是全 UI 的刷新上限来源。

## 滚动模式（scrollingWaveform）专项

绘制本身比整条模式更省：`isScrolling` 走中心锚点 + startIndex/endIndex 窗口，100 根柱子里只画屏内约 35 根（bar 7 + gap 2 = 9px/根，整首 900px，竖屏 `portraitWaveformOverflowScale` 1.2 放大到 1080px）。

**真正的瓶颈在回调链，不在绘制**：`PlaybackPage` 的 `onScrubbing` 走 `setState`（playback_page.dart:1125-1140），而 bar 每条 `onHorizontalDragUpdate`（waveform_progress_bar.dart:508）和抛掷惯性的每一帧（:268）都会回调 → 拖动期间指针事件级、抛掷期间 60Hz **整页重建**（PlaybackPage.build 从 990 行起，含封面轮播/歌词面板/可视化/Dock）。同一文件里精心做的「进度推进零 setState」在最需要跟手的这一刻被这条回调抵消。`_handleInteraction()` 还会每个事件重建 inactivity Timer。

修复方向：A) 把 scrubbing 值改成 `ValueNotifier<double?>` 下钻到 `PlaybackProgressSection`/`PlaybackOverlayProgressTimeLayer`，只让进度区局部重建（要动 4 个文件签名）；B) 最小改动：scrolling 模式下把 `onScrubbing` 节流到 ~100ms（与常态 8Hz 齐平，时间胶囊肉眼看不出差别）；C) 拖动/抛掷期间完全不回调，时间文本不跟手。

次要：`Transform.scale(scaleX: 1.2)` 在 `RepaintBoundary` 外层 → 层按原尺寸栅格化再被拉伸，横向轻微模糊 + 每帧多一次位图缩放；改 `canvas.scale` 可保矢量清晰，但手势 delta 要同步除以 overflowScale。

## 已落地：波形进度条内部优化（清单 1/3/4/5，只改 `waveform_progress_bar.dart`）

1. 悬停游标：`_hoverProgress`（double?）→ `_hoverProgressNotifier`（ValueNotifier<double?>），`onHover`/`onExit`/拖动里全部去掉 setState；游标线外包 `ValueListenableBuilder`，build 时返回 `Positioned` 或 `SizedBox.shrink()`（`ValueListenableBuilder` 不是 RenderObjectWidget，`Positioned` 仍能拿到 Stack 作为父数据宿主）。`onExit` 加「已是 null 就不写」判断。
2. 绘制：整条模式把柱子几何在 **build 阶段**录成两张 `Picture`（激活色/未激活色）缓存（`_WaveformPictureCache`，按 revision+size+barWidth+barGap+两色判等），`paint` 只做 2 次 `clipRect` + 2 次 `drawPicture`；滚动模式仍每帧建 Path，但改成「一条 Path + 左右互补 clip」，**删掉分界柱特殊裁剪逻辑**（两种模式同款分割，像素级对齐且更简单）。播放头 X：滚动模式恒 `size.width/2`，整条模式 `size.width*progress` —— 两处别混。
3. 淡入插值：`CurvedAnimation` 提前到 initState 建一次（`_waveformCurve`，dispose 释放）；`_animatedWaveform` 原地写入，不再每帧 `List.filled`。**连带要求**：initState 必须 `List<double>.of(...)` 拷贝，否则原地写入会改掉 `widget.waveform`（`_getEffectiveWaveform` 非空时直接返回入参本身）。
4. `shouldRepaint` 删掉恒等的 `progress` 比较，改用 `waveformRevision`；因为列表原地复用，`listEquals(oldDelegate.waveform, waveform)` 永远是同一个实例 → 必须靠 revision 判重绘，否则淡入动画不刷新。

验证：`flutter analyze lib/widgets/waveform_progress_bar.dart` 无问题；临时 widget test（非滚动绘制/滚动绘制/悬停游标出现与消失）3 项通过后已删除；`playback_audio_info_position_test.dart` 3 项通过。
`WaveformPainter` 是公开类，私有类型不能出现在其签名里（`library_private_types_in_public_api`）→ 缓存留在 State，painter 只收 `Picture?`。

## 修复：播放页背景模糊缓存 key 不含封面内容（`blurred_artwork_rasterizer.dart`）

结论先说：主播放页背景**不是**逐帧高斯模糊——`StaticBlurredArtwork` 用离屏 `Canvas + ImageFilter.blur` 预光栅化成 `ui.Image`（长边 160px、默认 sigma 30 折算约 12），LRU 缓存 6 首，`RawImage` 只做纹理贴图；切歌的 `AnimatedSwitcher` 淡入期间新旧两张都已是静态位图。仍是实时模糊的只有三处：小窗模式 `small_blurred` 的 `ImageFiltered(AppBlur.heavyFilter)`、小窗队列/歌词面板的 `BackdropFilter`、自定义图片背景（type 3，`playbackCustomImageBlurSigma>0`）。

原缺陷：缓存 key 只有 `songKey_sigma`，不含封面内容 → 播放中替换当前歌曲封面时，`didUpdateWidget` 触发了但 `getCached` 直接命中旧图，背景停在老封面（要等 LRU 淘汰 6 首或重启）。

改法（只动一个文件）：
- 新增 `BlurredArtworkRasterizer.fingerprintOf(Uint8List)`：FNV-1a 扫「长度 + 头 32KB + 尾 32KB」，开销与文件大小解耦。**不能用 `Uint8List.hashCode`**——`_prepareCurrentPlaybackArtwork()` 每次播放都新建实例，identity hash 会让每次切歌都重新光栅化。
- `_StaticBlurredArtworkState._resolveCacheKey()`：有 bytes 时用内容指纹（按实例 memo，`identical` 判重）；只有路径时退化为 `文件长度 + mtime`（`statSync`，仅 prop 变化时调用一次）。
- `_activeKey` 取代原来 `.then` 里重拼字符串的守卫，丢弃过期异步结果。

验证：`flutter analyze --no-pub lib/widgets/playback/blurred_artwork_rasterizer.dart` → No issues found。

## 远程媒体库下载路径审计（只读）

唯一落盘路径生成点：`remote_download_service.dart` 的 `buildLocalTrackPath()`（:251-318）。三档规则：

1. 有 `webDavPath`（WebDAV 传 `file.path` 绝对路径；SMB 传 `'${share}/${file.path}'`）→ 远端目录结构整体照搬，`<下载目录>/<远端全部层级>/<文件>`。
2. 否则（Subsonic / Jellyfin）→ `<下载目录>/<artist>/<album>/<NN - title><ext>`，空值回落 `Unknown Artist` / `Unknown Album` / `Track`。
3. 每段都过 `_sanitize()`（`\/:*?"<>|` → `_`），所以 artist/album 里的斜杠不会造出额外层级。

即「每首歌一个文件夹」在当前代码里不成立，只有两种现象来源：远端服务器本身就是一歌一目录（WebDAV/SMB 分支原样照抄），或该批曲目的 `album` 字段每条都不同（单曲型库 → 真的会一歌一夹）。

顺带发现（未修）：
- `collectionName` 参数在 `enqueueSubsonicTracks` / `enqueueJellyfinTracks` / `enqueueRemoteTracks` 里收下后**从未使用** → 专辑/播放列表下载不会建集合目录。
- Subsonic/Jellyfin 的扩展名推断失效：`song.path` 是 `subsonic://serverId/trackId`，`p.extension(uri.path)` 恒为空 → 一律回退 `.mp3`，FLAC 会被存成 `xxx.mp3`（`song.name` 里其实带着真实 suffix，`buildMusicFileFromSubsonic` 的 `suffix` 字段没被用于命名）。
- `_checkFileExistsLocally()` 只判「存在且长度 > 0」就标记 completed，不比对大小/内容，同名文件会误判已完成。
- 下载不写任何标签/封面文件，文件名完全来自远端 title + trackNumber。

**上面「每首歌一个文件夹不成立」的结论被实测证伪**（用户用 demo.navidrome.org 的 NCS: Infinity 下载到 `/Volumes/Untitled/music`）：

```
Alan Walker/NCS_ Infinity/...        Ash O'Connor/NCS_ Infinity/...
JPB feat. Joe Erickson/NCS_ Infinity/...   Tobu/NCS_ Infinity/01 - Candyland.mp3
```

14 首 → 14 个「单曲艺术家」目录。根因：`buildLocalTrackPath` 第一层取 `song.artist`，而合辑里每条 `artist` 都不同（Tobu / Mendum / JPB…），专辑级艺术家在 Navidrome 的 `albumArtists[0].name` / `displayAlbumArtist`（= "Various Artists"）里。服务端原始 path 就是 `Various Artists/NCS: Infinity/01-01 - Candyland.mp3`。

### 已修（3 文件）

1. `remote_media_resolver.dart`：新增 `extractAlbumArtist()`（`displayAlbumArtist` → `albumArtists[0].name` → `albumArtist`/`AlbumArtist`），Subsonic 与 Jellyfin 两条构造都写进 `MusicFile.albumArtist`。
2. `jellyfin_client.dart` `normalizeSongItem()`：补输出 `albumArtist`（`AlbumArtist` 字符串优先，其次 `AlbumArtists[0].Name`）——Jellyfin 侧构造拿到的是规范化后的 json。
3. `remote_download_service.dart` `buildLocalTrackPath()`：第一层改 `song.albumArtist ?? song.artist`；顺带修扩展名——新增 `_resolveExtension()` 优先从 `song.name`（`title.suffix`）取，只认 `MusicFileUtils.supportedAudioExtensions`，虚拟 URI 里取不到就回落 `.mp3`。原先 `p.extension('subsonic://id/trackId')` 恒空 → FLAC 一律被存成 `.mp3`。

验证：临时测试（真实 Navidrome json 片段）断言 `/music/Various Artists/NCS_ Infinity/01 - Candyland.mp3` 与 `13 - High.flac` 通过后删除；`test/player/remote/` 26 项全绿；三个改动文件 `flutter analyze` 无问题。注意 `flutter test` 会自动跑 pub get 把 `pubspec.lock` 的镜像源从 `pub.flutter-io.cn` 改成 `pub.dev`，跑完要 `git checkout -- pubspec.lock`。

### 三类下载入口的目录规则（已落地）

原状：`enqueueRemoteTracks` 只有一个从未被使用的 `collectionName`，路径一律 `artist/album`。后果是艺术家下载碰巧正确，歌单下载散成一堆单曲艺术家目录。

改为 `collectionFolder` + `groupByAlbum` 两个参数（`collectionName` 全删）：

| 入口 | 传参 | 落盘 |
|---|---|---|
| 专辑（详情页 / 右键） | 都不传 | `<下载目录>/<专辑名>/NN - 曲目.ext` |
| 艺术家（详情页 / 右键） | `collectionFolder: artistName` | `<下载目录>/<艺术家>/<专辑>/NN - 曲目.ext` |
| 歌单（详情页 / 右键 / 多选） | `collectionFolder: name, groupByAlbum: false` | `<下载目录>/<歌单名>/NN - 曲目.ext` |
| 多选批量 / 歌曲页全部下载 | 都不传（原来的 `server.name`、`l10n.songs` 是错的，已删） | 按各曲目所属专辑 |
