## Subsonic/Navidrome 关闭下载的适配（对应上游 PR #50）

**问题**：Navidrome `EnableDownloads=false` 时，`download.view` 仍回 HTTP 200，只是响应体换成
`{"subsonic-response":{"status":"failed","error":{"code":50,"message":"downloads are disabled"}}}`。
`_dio.download` 看到 200 即成功，错误体被当音频搬进音乐库并标记 completed（约 200 字节的"坏歌"）。

**决策**：明确失败 + Toast 提示，**不**静默回落到 `stream`（尊重服务端管理策略；PR #50 的做法是回落，未采用）。

**改动**：
- `subsonic_client.dart`：`errorDownloadsDisabled = 50`、`SubsonicException.isDownloadsDisabled`、
  `parseErrorBody()` / `parseErrorFile()`（后者只读 ≤64KB、非法 UTF-8 视为二进制）。
- `remote_download_service.dart`：`_dio.download` 之后、落盘判定之前嗅探错误体并抛出；
  catch 里 code 50 → 任务 error 用 l10n 文案 + 每个 server 只弹一次 Toast（`_downloadsDisabledServers`，
  成功下载后移除该 server 的标记）。临时文件由既有 `finally` 清理，故错误体不会落盘。
- `remote_media_resolver.dart`：转码 / AI 歌词走临时下载，同样嗅探并清掉 `transcode_temp/<id>` 目录再抛。
- l10n：`remoteServerDownloadsDisabled`，9 个 arb 同步 + `flutter gen-l10n`。
- 新增 `test/player/remote/subsonic_downloads_disabled_test.dart`（11 例，loopback 假 Navidrome）。

**环境注意**：本机 `HTTP_PROXY/HTTPS_PROXY` 指向 127.0.0.1:61086 时，`flutter test` 会以
"Unable to connect to flutter_tester process: Invalid WebSocket upgrade request" 全量失败。
跑测试前先 `unset HTTP_PROXY HTTPS_PROXY http_proxy https_proxy ALL_PROXY GLOBAL_AGENT_HTTP_PROXY`。

## 续：Jellyfin 侧「服务端拒绝下载」的实际情况

- Jellyfin 下载走 `_JellyfinDownloadSource.buildDownloadUrl` → `JellyfinClient.buildStreamUrl`
  （`/Audio/{id}/stream?static=true&api_key=`），**不是** `/Items/{id}/Download`。
  用户策略里的「允许下载」(EnableContentDownloading) 管的是后者，所以 Jellyfin 侧
  不存在 Subsonic code 50 那种「200 + 失败 JSON」，无需 fallback。
- Jellyfin 真正的拒绝方式是标准状态码：401（token 失效）/ 403（无权限）/ 404（曲目不可见或已删），
  Dio 抛 DioException，临时文件不会落盘（不会静默坏歌）。缺的只是文案。
- `remote_download_service.dart` 新增 `_describeHttpFailure(Object)`：401/403 →
  `remoteDownloadUnauthorized` + 每 server 提示一次（kind=`download_rejected`）；
  404 → `remoteDownloadTrackMissing`（只落到任务 error，不弹 Toast）。其余仍透出原始异常。
- l10n 新增 `remoteDownloadUnauthorized` / `remoteDownloadTrackMissing`（9 个 arb + gen-l10n）。
- 测试扩到 22 例（`_FakeNavidrome` 增加 `/Users/AuthenticateByName` 与 `downloadStatusCode`，
  `bootstrap` 增加 `serverType`）：Jellyfin 正常 / 403 / 404。
- **顺带发现的既有 bug（未修）**：`RemoteMediaResolver.downloadRemoteTrackToTempFile` 只判
  `type == subsonic`，其余全走 `WebDavClient`，于是 Jellyfin / SMB 曲目做转码或 AI 歌词时
  会用 WebDAV 的 URL 去下，必然失败。

## 远程播放链路审计：是否流式

结论：**是流式，不等整首下完**。链路：
`setUriResolver`（audio_service.dart:331）→ `resolvePlayableSource` 出 URL →
`AudioCoreController.resolvePlayableUri`（visualizer_player_controller.dart:477）→
HTTP(S) 一律套 `AudioStreamCacheProxy`（127.0.0.1 随机端口 `/stream?url=&headers=&cacheKey=`）；
SMB 已是 `LocalStreamProxy` 的 127.0.0.1 URL，会被跳过二次代理。
播放内核：桌面/iOS 是 `ffmpeg::format::input(url)`（ffmpeg_core/src/source.rs:109，边读边解码）；
Android 是 `MediaItem.fromUri` + ExoPlayer ProgressiveMediaSource。

既有行为（**都不是 bug**，已与用户确认）：
1. 未缓存曲目进代理时**同时开两条连接**：一条流给播放器，一条 `ensureBackgroundPrefetch` 全量落盘
   （audio_stream_cache_proxy.dart:212）——「尽快把整首缓存到本地」是设计意图。加上
   `playback_queue_processor` 的预取共用一个 `AudioStreamCacheManager`，`_activeDownloads` 去重，
   实际是两条而非三条。禁止再把它当隐患提。
2. 代理转发不等待消费：`_proxyUpstreamRequest` 只在最前 5 个 chunk `await flush()`，之后只 `add`。
   实测（本地回环，50MB / 客户端 2MB/s）：add-loop 272ms 跑完、工作集稳定不涨，说明多余数据滞留在
   socket/内核缓冲而非 Dart 堆。真实含义是「拉取速度由上游决定，与播放器消费节奏解耦」，
   与 ① 同一取向，不是缺陷。LocalStreamProxy 每 1MB await flush() 是「按消费节奏拉」，两者行为不同但都成立。
3. SMB 因是 127.0.0.1 被跳过渐进缓存，只靠 `remotePrefetchCount` 的全量预取；预取设 0 则每次都读远端。
4. `_serveLocalFile` 的 Content-Type 硬编码 `audio/mpeg`（缓存命中走本地文件路径，暂时无影响）。

### 为什么「下两遍」——根因

`_proxyUpstreamRequest` 转发循环本身是**上游速度驱动**的（实测 175MB/s 把整首拉完），
但字节**只转发不落盘**；缓存靠 `ensureBackgroundPrefetch` 另开第二条连接重新拉。
即：不是能力限制，是两套独立机制没有接线。改成写穿（tee）即可单连接同时满足
「播放按消费节奏」与「缓存按上游速度填满」。开销：Subsonic 配了 `maxBitRate` 时
两条连接会让服务端**并发转码同一首**（server CPU 白烧）。
当前并发量：播放中 = 1 流 + 1 全量下载 + 最多 `defaultRemotePrefetchCount`(2) 首预取。

### seek 语义（讨论，未落地）

播放器 seek = **关掉旧连接 + 新开一条带 `Range: bytes=N-` 的请求**到同一个代理 URL
（FFmpeg `http_seek` 重连；ExoPlayer `DefaultHttpDataSource` 每次 load 按播放位置拼 Range）。
所以纯写穿的后果：旧连接的 tee 写失败 → break → `.part` 作废，**seek 之后这次播放对缓存零贡献**。

关键不变量：`.part` 永远是「从 0 起的一段连续前缀 [0, X)」。有此不变量，
「seek 后另起一条补下载」就是 `Range: bytes=X-` + append，正确性无需额外论证；
真正要防的是同一时刻两个写入者 → 摘 tee 时**同步**置 `writeAllowed=false`（Dart 单线程，
检查/写入/累加之间不 await 即安全），再起补下载器。

硬前提：上游必须给 `Content-Length`（200，或 206 且起于 0）。Subsonic 配 `maxBitRate`
走服务端转码、Jellyfin 非 static 都是 chunked → 无 T → 不 tee，退回双连接。
故收益集中在外网 WebDAV 直连文件；SMB 走 `LocalStreamProxy` 另一条代理，不适用。

### 已落地：v1 写穿（tee）单连接缓存

改动（audio_core）：
- `audio_stream_cache_manager.dart`：新增 `StreamCacheWriter` + `beginStreamWrite()`。
  转发给播放器的 chunk 同步 append 到 `<cache>.part`；`written == expectedTotal` 才
  flush→rename→`pruneCacheIfNeeded`→`onTrackCached`。字节数不符（seek/挂断/上游截断）
  → `abort()` 删 `.part`，不占正式缓存名。
- `audio_stream_cache_proxy.dart`：`_handleRequest` 不再无条件 `ensureBackgroundPrefetch`；
  `_proxyUpstreamRequest` 先 `_expectedTotalBytes()`（200 用 Content-Length；206 且
  `Content-Range` 起点为 0 用 total），能 tee 就 tee，否则才退回「转发 + 第二条全量下载」。
  tee 失败（`complete()` 返回 null）再 `unawaited(ensureBackgroundPrefetch(...))` → **退化即现状**。
- 互斥：`_pendingStreamWriteKeys` 同步占位（`beginStreamWrite` 内有 await，不加会被并发请求穿透）；
  `ensureTrackCached` 先 `await writer.done` 再决定是否真下载，避免第三条连接。
- `pruneCacheIfNeeded`/`getTotalCacheSize` 排除 `.part`（`_isTransient`）；`proxy.start()` 里
  `cleanupStalePartFiles()` 清理 mtime > 1h 的残留 `.part`。

测试（`audio_core/test/audio_stream_cache_test.dart`，共 10 例全绿）：完整写入 rename、
字节不足丢弃 `.part`、同 key 单写入者、`ensureTrackCached` 等待 tee 不另连（用
`127.0.0.1:1` 不可达 URL 反证）、**顺序播放只发 1 次上游请求**、chunked 源退化 2 次请求。

已知阻塞（未修，非本次引入）：`flutter_taglib_metadata_bridge.dart:572` 用 `info.bitDepth`，
但 `flutter_taglib` 的 `AudioInfo`（master b4a08ad 与本地 1.6.0）都没有该字段 →
`flutter test` 整体编译失败。验证时临时置 null 跑完再还原，需用户决定是改 taglib 还是改调用点。

### 回归修复：波形/音频信息在播放结束前不出现

现象：不 seek 时，正在播放的远程歌波形进度条与音频信息一直空；seek 一下反而出现。

根因：`onTrackCached` 是波形/封面/元数据的**唯一**触发点
（`AudioService._handleRemoteTrackCacheReady` → `processRemoteCachedMetadata` +
`getWaveformData(localFilePath: file.path)`）。v1 把 `writer.complete()`（rename + 回调）
放在 `request.response.close()` **之后**，而 `close()` 要等播放器把响应缓冲排空 —— 对一首
4 分钟的歌就是 4 分钟。数据其实几十秒就到齐了，只是没 rename。seek 会中断 tee →
`abort()` → 回退 `ensureBackgroundPrefetch` → 第二条连接全速下完 → 回调立刻触发，所以
「seek 才显示」。`WaveformService.getWaveformData` 另有 `isRemote && effectivePath == null`
时直接返回空波形的短路（waveform_service.dart:74）。

修法：`try { await for(...); await writer.complete(); } finally { await response.close(); }`
把收尾固化成 close 之前，顺序不会被后人挪动。

顺带修：`unawaited(ensureBackgroundPrefetch(...))` 的异常无人接，`_doBackgroundPrefetch`
里的 `rethrow` 会漏成调用方 zone 的未捕获异步错误（测试里表现为随机让**下一个**用例失败）。
抽出 `_startBackgroundPrefetch()` 用 `then<void>(_, onError:)` 吃掉错误。

测试：删掉一个用于验证该时序的 4MB 集成用例 —— 客户端完全 pause 时 `HttpResponse.add`
会因 socket 窗口关闭而背压，用例时快时慢（4/5 通过），无法作为基准；时序改由代码结构
（try/finally）保证。`setUp` 的缓存上限从 1MB 调到 64MB（"prunes" 用例显式传 limitBytes，
不受影响）。最终 `audio_stream_cache_test.dart` 10 例，连跑 5 次全绿。

### 修复：进播放页背景封面「闪一下」（Navidrome）

日志 `run.log` 证据链（同一首 2bs7utGKp4y…）：
`bg inputs bytes=112701` → `cache miss …1b83d` → `apply image=A` →（tee 缓存就绪）
→ `bg inputs bytes=47889 thumb=…jpg` → **`blurred artwork | init`（State 重建）**
→ `cache miss …bb11` → `apply image=B`；随后 `bytes=112701` 又切回 A。

三个真因，全部已改：

1. **层身份被换掉**（`playback_page.dart` `_SafeBackgroundSwitcher`）：in-place 更新时
   `_items[last] = _SwitcherItem(child: ...)` 新建了 item，而 Stack 子节点用
   `ObjectKey(item)` 匹配 → 整棵背景子树销毁重建 → `StaticBlurredArtwork._blurredImage`
   归零 → `build` 返回黑色 fallback，直到重新光栅化完成。日志里每条 bg 变化后都跟一次
   `init` 就是这个。改法：`_SwitcherItem.child` 改可变，只替换 child 不换 item。
   （顺带解释了此前每次 rebuild 都重新算指纹、重建 RawImage 的开销。）
2. **旧层 wrapper 类型漂移**：非最后一层用 `KeyedSubtree`、最后一层用 `FadeTransition`，
   新层插入时旧层 runtimeType 变化 → 元素重建 → 旧层变黑，正好垫在新层淡入下方。
   改成所有层统一 `FadeTransition(opacity: item.animation)`。
3. **封面字节来回横跳**（`audio_service.dart`）：`_prepareCurrentPlaybackArtwork` 用
   **入参快照** `song.artworkBytes`（可能是 null）走缩略图兜底，再无条件覆盖
   `currentSong.artworkBytes`；`_updateCurrentMetadata` 同样用缩略图字节覆盖 hi-res。
   新增 `usedThumbnailFallback` 标记：缩略图兜底且已有更大字节时保留原值。
   112701(服务器封面) ↔ 47889(缩略图) 的横跳由此消失。

兜底：`_StaticBlurredArtworkState` 换图改成 260ms 交叉淡化（`_outgoingImage` +
`_crossFade`），且 cache miss 时**不清空** `_blurredImage`，即使还有别的来源变化也不会黑帧。

验证：`flutter analyze` 三个文件零问题。`flutter test` 仍被 `flutter_taglib` 的
`AudioInfo.bitDepth` 编译错误挡住（非本次引入），所以没跑 widget 测试；
需要真机看日志确认：同一次播放内 `blurred artwork | init` 应只出现一次，

未做（可选）：根因之一是 `audio_stream_cache` tee 让缓存回调提前到 1~2s，

### 定位当前播放：远程歌曲统一走「解析专辑 → 开专辑详情页」

用户反馈同一操作有三种结果（跳详情页 / 提示不在扫描目录内 / 毫无反应）。定位到的根因：

1. `SongLocatorHelper.locateCurrentPlayingSong` 的 Subsonic/Jellyfin 分支把「服务器被删、
   getSong 超时或 404（客户端 `catch(_) { return null; }` 全吞）、albumId 缺失、context 已卸载」
   全压成同一句 `songNotInScannedFolders`；Jellyfin 的 `albumId` 恒存在（可能是空串），
   `?? parent` 不回落到空串 → 拿 '' 去开专辑页。
2. 「毫无反应」有两处：`highlight()` 对同值不通知（riverpod 默认 `previous != next`），
   而远程页只在 `widget.highlightedSongPath != oldWidget.highlightedSongPath` 时滚动；
   以及 `remoteServersProvider` 冷启动未加载完时 `asData ?? []` 直接判成「找不到服务器」。
3. WebDAV/SMB 分支本身没有失败出口，用户实测可用，未改。

改法（`lib/utils/song_locator_helper.dart`）：新增 `_openAlbumForRemoteSong`，
Subsonic/Jellyfin 只此一个出口——`getSong` 解析 albumId/parent（都做 `isNotEmpty` 校验）→
开专辑详情页并高亮；解析不到统一 toast 新文案 `remoteAlbumUnavailable`
（9 个 arb 同步 + `flutter gen-l10n`）。服务器列表改 `_loadedRemoteServers()` 等待加载；
加静态 `_isLocatingRemoteSong` 防连点重复压页；补 `[Locate]` debugPrint 日志。
目录页、远程库页、专辑页现在共用同一路径（专辑页对「当前就是该专辑」仍只滚不压新页）。

坑：**arb 是 CRLF**，用 Python 批量改必须保留行尾，否则整份文件 EOL 翻转。

### run.log 19 个测试失败的根因（截图测试）

- 全部集中在 `test/widgets/*screenshot*`，每个用例固定报 **2 条**异常，报错发生在截图已写盘之后（`SUCCESS_*_SAVED` 已打印），所以是纯异常导致判失败，产物没问题。

  只显示过一张位图（没触发交叉淡化）的实例，`_crossFade` 从未被读，`dispose()` 里 `_crossFade.dispose()`（:434）才第一次求值 →
