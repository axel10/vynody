## 安卓进目录动画「冷启动卡、之后不卡」——profile 实测结论

**Dart 侧被排除，瓶颈在 raster 线程。** 之前怀疑的「重复加载」是错的，实测否掉了：

- `[FoldersPage][timing] navigateTo` 四次全是 **0 ms**（system → Download → lib → 专辑目录）。
- `loadRootFolderSongs` 只有启动期一次 `RELOAD /storage/emulated/0/Music songs=374 db=23 build=3 sort=0 apply=0 notify=0 total=27`（`scannedTreeBefore=false`），并发生在扫描阶段，不在进目录路径上。所以「扫描不回填 `_loadedRootPaths`」确实存在（会多付 27ms），但**不是卡顿原因**，不必为它改架构。
- 全部超时帧都出现在 `[Frame][timing]`：单帧 32~133 ms，**raster 20~99 ms，build 多数 0~8 ms**（仅新页首帧 build 26~63 ms）。

分组看，raster 成本和「banner 有没有封面图」强相关：

| 页面 | 是否有封面 banner | raster 区间 |
|---|---|---|
| system | 有 | 37~65 ms（连续 6 帧高位） |
| system/Download | 有 | 34~71 ms |
| system/Download/lib | 有 | 22~99 ms |
| 最深专辑目录 | 无 | 17~32 ms |

连续 5~8 帧都停在 40~70 ms（不是前两帧高峰后回落）→ 不是一次性解码，是**每帧重算**。

指向：`folder_header_banner.dart` 的 `ImageFiltered(imageFilter: AppBlur.heavyFilter)`（sigma 16，全屏宽 × ~200dp）在转场缩放期间每帧失效重算；`main.dart:649` 的 `ZoomPageTransitionsBuilder(allowSnapshotting: false)`（为修返回时水波纹残留）让转场每帧全量重绘，把这段模糊成本直接暴露出来。

次生基线（无封面的页面仍有 20~30 ms）：目录项封面 `FolderZoomItem` 传 `size: 200` → 解码桶 250dp × dpr（手机 750px），实际网格封面远小于此；外加每项 `ClipRRect` / 阴影合成。

待定改法（等用户点头）：banner 背景改「64px 小图解码 + sigma≈4」替代实时 heavy blur；目录项解码桶降到 120dp 档。

临时埋点仍在（`!kReleaseMode` 包裹，release 会被 tree-shake）：
- `scanner_service.loadRootFolderSongs`：skip / RELOAD 分段计时
- `folder_page._navigateTo`：导航耗时
- `folder_page._handleFrameTimings`：仅导航后 2s 窗口内、单帧 ≥32ms 时打印 build/raster

## 竖屏进目录 banner 转场期间空白（同日后续）

现象：竖屏进子目录，push 转场（~300ms）期间 banner 背景整块空着，动画结束才出现封面。

根因（均在 `folder_header_banner.dart`）：
1. `_loadHighResArtwork()` 把应用高清推迟到 `ModalRoute.animation` completed（旧注释「避免转场中 setState 卡顿」），等于整个转场都不显示高清。
2. `_buildBannerImage()` 的 `Image.memory/file/network` 没有 `frameBuilder`/`errorBuilder`：解码未完成 = 空白，文件读不到 = 也空白。
3. `_resolvedPath` 直接 `File()`，没过 `ScannerPathUtils.resolveIosSandboxPath()` → iOS 沙箱路径漂移后静默空白。

改法：
- 去掉「动画完成才 apply」的延迟，直接 setState（`gaplessPlayback: true` 保证替换不闪）。
- `_buildBannerImage` 改成「provider + frameBuilder 铺底」：高清未就绪时先画**低清 seed**，`errorBuilder` 也回落 seed。
- seed 与网格条目**同 key**：`ResizeImage(FileImage(path), width|height: thumbnailBucketSizeFor(kZoomItemThumbnailSize) * dpr)`。同 key → 命中 ImageCache → `wasSynchronouslyLoaded` → 转场第一帧同步出图。
- 尺寸方向必须与 `SongThumbnail` 同源（都读 `metadataMap` 的 `artworkWidth/Height`）；方形封面两边若一个走 cacheHeight、一个走 cacheWidth，key 不同就不命中。
- `song_thumbnail.dart` 抽出顶层 `thumbnailBucketSizeFor(double)`，`_bucketedSize` 改调它（单一来源，别处别自算 cacheWidth）。

关联：Android 侧 `ZoomPageTransitionsBuilder(allowSnapshotting: true)` 会让转场画面趋于「首帧即定」，所以**第一帧有没有图**比「多久解出来」更关键。

顺手发现（未改）：
- `heroTag` 从 `FolderHeaderBanner` 传到两个子 banner 后从未使用（没有 `Hero` 包裹），是重构遗留的死参数。
- `_updateAspectRatioFromFile` 用裸 `FileImage` 解码整张原图只为读宽高，进页面多付一次大图解码。




## banner 背景模糊层参数修正（10:52）

上一轮把 `_kBannerBackdropDecodeScale` 压到 0.125（1080 物理宽 → 解 135px）、sigma 压到 6，实机出现**肉眼可见马赛克**。

原因是几何关系没算清：解码图被拉伸到整宽显示，**单像素块尺寸 = 1/(dpr × scale) 逻辑像素**。scale=0.125、dpr=2.75 时块 ≈ 2.9dp，而 sigma 只有 6，块边界落在 2σ 以内 → 高斯糊不住块边缘。

定则：**放大后的块尺寸必须远小于 sigma**。现值 `scale=0.5`（块 ≈ 0.67dp）+ `sigma=16`（低端机 10），块完全不可见。

另一个认识：`ImageFilter.blur` 的高斯作用在**屏幕区域**、与源纹理分辨率无关，所以压解码宽度只省解码/上传，换不到模糊本身的光栅收益——不值得为此牺牲画质。

## 淡入策略反转：全类型统一「就位即淡入」（13:20）

上一轮为了滚动 raster 关掉了目录页条目的淡入（`fadeInOnLoaded: false`）。用户要求改成**一律淡入**：不管歌曲、文件夹还是其他地方，缩略图只要没就位（没生成 / 没生成出来但没解码），就位并出现时都走同一个 280ms `easeOutCubic` 淡入；确实没有封面则淡入默认图标。

- 新增 `lib/widgets/artwork_fade.dart`：`kArtworkFadeInDuration`(280ms) + `artworkFadeInFrameBuilder`（首帧到达前不绘制、首帧到达后淡入；`wasSynchronouslyLoaded` 直接给 child，避免滚动时整片抖动）。

- `artist_avatar.dart`、`remote_artwork_widget.dart` 同步接入。远程走网络，等不起空白，用「占位垫底 + 封面淡入覆盖」的交叉淡入（`_withFallbackUnderlay`），errorBuilder 改成 `SizedBox.shrink()` 让垫底的占位露出。
- `folder_zoom_item.dart` / `folder_list_tile.dart` 去掉 `fadeInOnLoaded: false`。

代价（预期内）：目录页滚动起头又会多出 N 个 `AnimatedOpacity` 的 saveLayer，上一轮测到的 8~14 层 / raster 40ms+ 会回来一部分。若实机卡顿，可考虑只对「目录页条目」恢复 `_holdLastFrame` 式跳过，而不是全局关淡入。

## folder_entries 收尾三条（同一轮续）

评估后确认：这次改造是「结构 + 显示正确」的收益，不是算力收益。实测（5 万歌 / 5000 目录 /
3 根，macOS sqlite3）：旧 6 条聚合 ≈24ms（`LIKE 'root/%'` 用不上 BINARY collation 索引，
`EXPLAIN` 是 `SCAN songs`）；新冷启动读 5000 行 ≈5ms，写 5000 行 ≈10–40ms —— 净基本打平。

收尾做了三件事：
- `_persistFolderIndex` **只写统计，不写封面**。原来那段 walk 采 `representativeSongCache`，
  但 `notifyListeners()` 的 `invalidateCache()` 会把它清空，800ms 防抖后采到的是空集或
  不确定子集 —— 典型的「看起来在做、其实没做」的死路径。封面唯一写入口 = `_refreshFolderCoversForRoots`。
- 就地删歌后补落盘：`ScannerMetadataStore` 新增 `onVisibleTreeSongsRemoved`（只在真的删到东西时回调，
  `_removeSongsFromFolder` 改为返回 bool），宿主 `_scheduleFolderIndexPersistForRemovedSongs`
  按受影响根 `invalidateCache()` + 复用 800ms 防抖整树重写。**禁向上冒泡**：树在内存里，
  整树 O(N) 比维护增量路径安全，同批删除只写一次。
  注意 `songCount`/`totalDurationMs` 是惰性记忆化字段，删完不先失效会把旧数字写回库。
- `searchFolders` 改读表：新增 `getFolderStatsForPaths`（一次 IN，分块 500，键按
  `resolveIosSandboxPath` + normalize 统一，`statsValid=false` 不返回）。缓存未命中才退回
  `getSongCountUnderPath`（该目录还没落盘过）。
