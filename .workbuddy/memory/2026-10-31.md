## zoomable_sliver_grid：网格↔列表「条目位置跳变」的真因（内容交接不透明度与滞回阈值不同源）

**现象**：捏合/换档动画中途，条目内部（标题、封面）会瞬移一截；条目盒子本身是平滑的。

**定位方法**：`flutter test` 里逐帧量 `tester.getRect(find.text('T2')).top` + `metrics.contentReveal`
`metrics.contentIsGrid`。点击动画 0.667→0.5 实测：交接帧 `morph=0.406` 时标题从 `(165,199)`
瞬移到 `(154,235)`（**+36px**），而当时的 `contentReveal` 还有 **0.90**。

**根因**（`zoom_layout_utils.dart`）：
- 内容换布局发生在滞回阈值 `kFolderZoomContentHandoff{Upper,Lower}` = 0.55 / 0.45；
- 但压暗量按 `|morph - 0.5|` 算，**零点错位 0.05**，于是换的那一刻不透明度还有 0.74~0.90；
- 两套内容排版（封面在上+标题在下 / 封面在左+标题垂直居中）只能整份换、不能插值，
  所以在 90% 不透明度上硬切 = 肉眼看到"跳一下"。
- 帧步进还会越过阈值一截（0.525 → 0.406，一跳跨过 0.45），只按阈值算这一帧又回到 0.37。

**修法**：
1. `kFolderZoomContentHandoffMinOpacity` 0.55 → **0.0**；
2. `_resolveContentHandoff` 的压暗零点改成"距滞回带边界的距离"（带内恒 0，带外 0.12 内线性恢复）；
3. 新增 `_handoffFlipMorph`：记录**真的翻面那一帧**的 morph，压暗距离取
   `min(距带边界, 距翻面点)` —— 兜住帧步进越阈值。翻面在新手势 / `_applyTargets(animate:true)` 时复位。
4. 同一类不一致：捏合冻结表（`_resolvePinchPinning`）的 `targetViewportTop` 从
   `viewportTopForLayer`（带 `maxScrollOffsetFor()` 上界夹取，而那个值不含外层 `SliverPadding`
   尾部 padding，贴底实测少 16px）改为 `solveViewportTopFor`（与 `_pinchTargetPixels` 同源）。

**验证**：新增 `test/zoom_content_handoff_test.dart`（两个方向断言「换布局那一帧 reveal < 0.02、
前一帧 < 0.4」）；插件 `flutter test` 38 全绿；`flutter analyze lib test` 干净。

**顺手记录**：
- 条目盒子几何本身在点击/捏合两条路径都平滑：混和几何在两端口权重处与 per-layer 视口夹取无关
  （基准是真实 `viewportTop`，残差由 `correction` 吸收），所以"跳"只可能来自权重跳变、
  contentCount/宽度跳变、或本次的内容交接。
- 产品侧 `test/widgets/folder_zoom_geometry_trajectory_test.dart` 的
  「带 SliverPadding 的多档连点」**本来就是红的**（stash 掉本次改动复跑确认）：
  `resolveItemTransition(10).isShared` 期望 true 实为 false —— 条目 10 被判成淡入锁定，
  屏幕上会"出现在终点"而不是滑过去。多档连点时可能仍是跳变源，待查。

## 捏合第一帧整屏下掉（目录页）：底部避让 Dock 的 padding 被当成了夹取上界

用户反馈上一轮的内容交接修复后问题依旧：**捏合第一帧条目整体往下掉一段**，目录页。

**复现**（`zoomable_sliver_grid/test/zoom_tail_padding_test.dart`）：banner 220 + `SliverPadding(top 8, bottom 160)`
+ 18 个文件夹（4 列，内容总高 786 < 视口 800），滚到底：`px=374 top=146 anchor=none`，
捏合第一帧 `0..3` 条目 **+146px**。把 `bottom` 改成 0 就不再掉。

**根因两条，都在 tracker 里**：
1. `_recordAnchor()` 判"底部贴边"要求 `maxScrollOffsetFor() > 0.5`（内容必须比视口高）。
   目录页文件夹少 + 底部一大块避让浮动 Dock 的 padding 时，内容比视口矮
   （`contentExtent - viewportHeight` 为负），这个门槛直接判不中 → 锚点落到 `none`，
   锚条目按"视口顶部还在内容里"去取，取到的位置根本不在内容里。
2. `viewportTopForLayer()` 又把视口顶部 `min(top, maxScrollOffsetFor())` 夹回内容范围 ——
   而 `maxScrollOffsetFor` 是"内容总高 − 视口高"，**不含外层 `SliverPadding` 的尾部 padding**
   （真实 `maxScrollExtent` 含它）。于是夹取差了整整一个 padding。
   单层稳态帧用的是真实 `viewportTop`，一进入捏合分支（两层混合）改用夹过的值 →
   第一帧整屏下掉那一段。

**改法**：
- `_recordAnchor` 判底改成"内容末端进了视口"：`viewportTop >= contentExtent - viewportHeight - 0.5`
  （内容比视口矮时该值是负数，同样成立）；`contentCount` 还没回填（首帧）时不判底。
- tracker 新增 `tailExtent`（内容末端之后还能滚多长）+ `scrollMaxPixelsReader`
  （`ScrollPosition.maxScrollExtent`），只在单层稳态刷新：`(maxPixels - precede) - (内容总高 - 视口高)`。
- 新增 `maxViewportTopFor(layer) = maxScrollOffsetFor(layer) + tailExtent`，
  `viewportTopForLayer` 的夹取上界改用它；`_resolvePinchPinning` 的 `targetViewportTop`
  改回 `viewportTopForLayer`（现在与布局同源了）。

**验证**：新测试 5 例（短内容/长内容/无 padding/贴底放大/顶部），全绿；插件 `flutter test` 43 全绿；
`flutter analyze` 干净；参数扫描（2 档 × 5 个条目数 × 4 个滚动位置 × 2 种底部填充，只统计 shared 条目）
首帧与次帧位移差全部 0.0px。产品侧仍是那一个既有失败（多档连点 pinning 判定）。

## 目录页适配 zoomable_sliver_grid 的「一页多列表」

包侧的 `section` 机制已是现成的（`SliverAnimatedZoomGridDelegate.section` +
`ZoomItemScaffold.section`，滚动补偿按页面坐标结算），但产品侧目录页一直是
**每个列表各自一个 `FolderZoomSliverBuilder`**：`folder_detail_view` 是「子目录 + 歌曲」，
`folder_root_view` 是「根目录 + 云服务器 + 搜索歌曲」。症状就在这个结构上 ——
上游那一段在下游的 tracker 里根本不存在，换档时下游只按自己的局部坐标补偿，
被上游的 `ΔH` 顶走；两个 builder 还会同时往同一个 `ScrollPosition` 写像素值，谁慢谁赢。

**改法**：
- `folder_layout_utils.dart` 新增 `ZoomSectionHost`：传了 `metrics` 就直接画，
  没传才自建 builder。列表组件只多两个字段（`metrics` / `section`），
  `build` 里的 `FolderZoomSliverBuilder(` 改成 `ZoomSectionHost(`，其余一行不动。
- `FolderSubfoldersSliver` / `FolderSongsSliver` / `RemoteServersSliver` 各加
  `metrics` + `section`；`FolderZoomItem` / `SongZoomItem` / `RemoteServerZoomItem`
  透传 `section` 给 `ZoomItemScaffold`。
- 两个目录页把 builder 提到 `CustomScrollView` 之上：顺序必须是
  `FolderZoomGestureLayer` → `FolderZoomSliverBuilder(controller: _localScrollController)` →
  `RefreshIndicator` → `CustomScrollView`。**layer 必须在 builder 外面**，
  否则 `FolderZoomPinchScope.maybeOf` 拿不到（捏合不跟手）。
- 各段 section 常量：`folder-detail.folders` / `folder-detail.songs`；
  `folder-root.folders` / `folder-root.servers` / `folder-root.songs`。
- 排序模式（reorderable grid）那几条分支**不传** `section`：它们不走缩放 delegate。

**未做**：`remote_folder_browser_page`（WebDAV 目录）还是两个 builder，
同一个坑；`WebDavSubfoldersSliver` / `WebDavSongsSliver` 照上面三步改即可。

**代价**：builder 的 `setState` 现在会重建整个 `CustomScrollView` 子树（以前只重建各自 sliver），
260ms 过渡期约 16 帧。若真机掉帧，把页头/横幅那几个 sliver 预先构造成 widget 实例
再在 builder 里复用（identical 会短路 `Element.updateChild`）即可。

## 把「一页多段」的适配收回包里

上一版是在项目侧补的：`folder_layout_utils.dart` 里写了个 `ZoomSectionHost`，
三个列表组件各加一个可选 `metrics` 字段，页面手工把它传下去。问题是这套东西本该属于包——
包只提供了 metrics，没提供「让子孙知道页面上已经有一个 builder」的通道，于是每个项目都得自己搭。
可选参数还有个更贵的问题：漏传不会报错，页面会静默退回「每段一个 builder」，
表现成切档时列表甩一下，看起来像手感问题。

**包内新增**（`zoom_layout_utils.dart`，`FolderZoomSliverBuilder` 之前）：
- `FolderZoomMetricsScope`（InheritedWidget）：`FolderZoomSliverBuilder` 的两个
  `return widget.builder(context, metrics)` 出口都包上它，两种分支（捏合 / 稳态+动画）都要包。
- `FolderZoomSectionHost`：`FolderZoomMetricsScope.maybeOf(context)` 有祖先就直接画，
  没有才 `return FolderZoomSliverBuilder(...)`。判据是**树的位置**，不是参数。
- 文档 / README / CHANGELOG / 示例同步；新增 `test/zoom_section_host_test.dart` 2 例
  （多段共用一个 builder 且两段拿到 `identical` 的 metrics；无祖先时自己就是宿主）。
- 包全量 `flutter test` 52 例通过（原 50 + 新 2）。

**项目侧回退**：删掉 `ZoomSectionHost`；`FolderSubfoldersSliver` / `FolderSongsSliver` /
`RemoteServersSliver` 去掉 `metrics` 字段与构造参数，`build` 首行改
`FolderZoomSectionHost(zoomScale:, width:, builder:)`；两个目录页删掉 `metrics: zoomMetrics`，
builder 参数改成 `(context, _)`。section 常量原样保留。
`flutter analyze lib` 仍是 135 条（全是原有 info/warning），冒烟 + 返回键 22 例通过。

**遗留**：`remote_folder_browser_page.dart` 仍是「子目录 + 文件」两个 builder，
`WebDavSubfoldersSliver` / `WebDavSongsSliver` 照上面三步（去掉 metrics 字段不存在、直接把
`FolderZoomSliverBuilder(` 换成 `FolderZoomSectionHost(` + 页面提 builder）即可。

## 播放页拖动卡顿（DevTools timeline + cpu profile 定位）

现象：Android profile 包，拖动顶部把手收起播放页，全程 ~27fps（帧间隔稳定 33ms）。

数据（用户给的 devtools 导出）：

- timeline：713 帧里第 685–791 帧是拖动窗口（3.9s / 106 帧）；拖动时 build 9–23ms、
  raster 7–15ms，**非拖动时 build 仅 0.2ms**。
- cpu profile（1.33s / 3810 采样）：`drawFrame` 占 71%，其中
  `_LayoutBuilderElement._rebuildWithConstraints` 链占 **54%**，`flushSemantics` 占 **13%**
  （该设备开了无障碍服务，语义树常驻）。重建链平均深度 112 帧，整页无一幸免。

根因两条：

1. `_handleVerticalDragUpdate` 每个指针事件 `setState(_dragOffsetY)`；收起动画监听器也每帧
   `setState` → 整页重建（`_dragOffsetY` 只被 `Transform.translate` 用到）。
2. 页面 `build()` 顶层是 `OrientationBuilder`（内部就是 `LayoutBuilder`）：
   `_LayoutBuilderElement.markNeedsBuild` 把整棵子树的重建推迟到 **layout 阶段**，
   任何页面级 setState 都要在布局期再全量重建一遍。

已改（`lib/pages/playback_page.dart`）：

- A：`_dragOffsetY` → `ValueNotifier<double> _dragOffsetNotifier`；拖动/收起动画只写 notifier；
  `Transform.translate` 用 `ValueListenableBuilder` 包住并把 `pageContent` 走 `child`。
- B：`OrientationBuilder` → `Builder` + `size.width > size.height` 判方向
  （本页恒为 Scaffold body，约束＝窗口尺寸，等价；保留 Builder 只为不改 570 行缩进）。

验证：`flutter analyze lib/pages/playback_page.dart` 干净；`test/widgets/playback_screenshot_test.dart`、
`test/widgets/back_press_navigation_test.dart` 通过。

未做（待定）：`Listener.onPointerMove/Hover` 每个事件 `resetInactivity()` 都 cancel+新建 Timer；
build 里 `File(path).existsSync()` 同步 IO；`ref.watch(settingsServiceProvider)` 过宽（1010/1060 两处）；
raster 那 ~9.5ms（整页平移 + 全屏背景重绘）要再压得动背景层或加 RepaintBoundary。

### 第二轮：C/D/E 已落地，702ms 停顿查不动（数据没覆盖）

- C：`_handleInteraction({bool throttled})`，`onPointerMove/Hover` 走 `throttled: true`，
  最小间隔 `_interactionThrottleMicros = 500ms`（按上次真正 reset 的时间戳算，节流命中时不更新时间戳）。
- D：只做了一半——删掉 `Builder` 里重复的 `ref.watch(settingsServiceProvider)`
  （同一 element 订阅同一 provider 本来就只有一份依赖，这处是写法误导）。**真正收窄做不了**：
  页面确实读 `settings` 十几个字段（isSmallWindowMode / 两个 tip 标记 / 背景色、模糊 sigma、
  smallWindowBottomPanelMode…），要收窄得先把 `SettingsService` 拆成按字段分组的 provider，
  属架构改动，没动。
- E：新增 `_pathExists(String?)`（`Map<String,bool>` 缓存，≥512 条整体清空），
  收口 5 处 build 期同步 `existsSync()`（自定义背景图 1 处 + 背景解析链 4 处）。
  文件运行期被删时缓存残留 true，由 `Image.file` 的 `errorBuilder` 兜底。

**702ms 单帧（第 745 帧）**：`vsyncOverhead = 685.5ms`，build 7.0 / raster 9.8
（p50 0.85ms、p90 2.7ms、max 685.5）→ 帧本身正常，是 UI 线程在起帧前被卡了 685ms。
两份产物都覆盖不到：把 timeline 的 `performance.traceBinary` 按 perfetto TracePacket 解出来
（field 1 包 → field 8 时间戳 ns、field 11 → 23 名字 + 9 类型 + 22 分类，共 19964 个事件），
事件时间范围 `318844.1s ~ 318909.8s`，而停顿在 `318910.591s` —— **录到的 trace 正好在停顿前
776ms 结束**；cpu profile 又是 13 秒之后的另一次采集。另：`lib/widgets/playback/` 与
`lyrics_panel.dart` 里没有任何 `toByteData` / `toImageSync`，排除同步图像操作。
下次要抓得加 `SchedulerBinding.addTimingsCallback` 看门狗（记 vsyncOverhead > 100ms）或重录。

## 目录页缩略图在 macOS 上发糊（已修）

**根因**：`kZoomItemThumbnailSize = 120` 是硬编码解码尺寸（`thumbnailBucketSizeFor(120) * dpr`，
2x 屏 = 240px 纹理）。但网格封面真实边长 = 网格卡片宽度（`ZoomItemScaffold` 的
`gridCoverSize = min(W, H - 文字高)`），而 `calculateCrossAxisCount` 横屏分支写死 6/7/8 列、
**不看窗口宽度**：macOS 1200dp 窗口 → 卡宽 181dp（362px），1728dp → 269dp（538px）。
240px 纹理放大 1.9 倍 + `FilterQuality.low` ⇒ 明显发糊。该常量注释里「卡片只有 100~180dp」
只对手机成立；专辑页 `album_zoom_item.dart` 一直用 250，所以没这个毛病。

**修法**（解码尺寸跟随真实卡宽）：
- `folder_layout_utils.dart` 新增 `zoomItemThumbnailSizeFor(metrics)`：判据
  `metrics.isGridTarget`（换档动画期间恒等于**目标**档位，一次换档只切一次桶），网格态取
  `max(getFolderListCoverSize(targetZoomScale), targetCardWidth)`，列表态只取列表封面尺寸。
- `folder_zoom_item.dart` / `song_zoom_item.dart` 不再传 `kZoomItemThumbnailSize`。
- `folder_header_banner.dart` 新增 `thumbnailSize` 参数喂 seed 分桶；`folder_detail_view` /
  `folder_root_view` 把 builder 的 `metrics` 传下去（`builder: (context, _)` → `(context, metrics)`）。
  **banner 首帧 seed 必须与条目同源**，否则退回「等一次解码」。
- `kZoomItemThumbnailSize` 降级为 banner 默认兜底值，注释已改写。
- 回归测试 `test/widgets/zoom_item_thumbnail_size_test.dart`（4 例）。

**效果**：macOS 120→250 桶（500px，正好等于 `vynodyArtworkThumbnailSize = 500` 的上限）；
手机竖屏 112dp 卡仍 120 桶不涨内存；手机横屏 6 列 ~150dp 会升到 250 桶。

**待议**：① `calculateCrossAxisCount` 横屏固定 6/7/8 列不看宽度，4K 全屏卡宽可到 300dp+，
既是糊的根因也让大屏只排 6 列；② `vynodyArtworkThumbnailSize = 500` 在 >250dp 卡宽 + 2x 屏下
已逼近上限，再大档位或更高 DPI 需要提升缩略图落盘尺寸（会触发全库重新生成）。
