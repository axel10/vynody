## mesh_flow 背景「蓝色比原图任何部分都艳」根因定位

`mesh_flow/lib/src/cover_processor.dart` `_applyColorTuningAndBlur()` 是**在 gamma 编码 sRGB 值上做的一串乘性变换 + 逐通道 clamp**，净色度系数可算成常量：

```
0.5(预压缩) × 2.6(saturation) × 1.4(contrast) × 0.8(kBright) ≈ 1.456
```

即 `saturation: 2.6` 实际只给 **×1.46 的 Lab 色度**，但它对所有像素一视同仁，再叠加 `:262-264` 逐通道 `clamp(0,255)`，暗色相有大量向上余量 → 深色大面积区域吃满增益。

实测（OneRepublic - Take Care Of You 封面，32×32 降采样 + 完整管线复算）：

| 指标 | 原图 | 调色后 |
|---|---|---|
| 整张最高 C* | 73.6（粉云 rgb(227,96,211)） | 100.2（天空蓝紫 rgb(151,64,241)） |
| 天空区峰值 C* | 63.3 rgb(65,87,192) | 91.3 rgb(43,75,228) |
| 天空区平均 C* | 44.0 | 62.8 |
| 通道跌出 [0,255] 被硬 clamp | — | 229/1024 (22%) |

「蓝色最艳」= 蓝是 61% 面积的大块平坦区（4×boxBlur 摊薄不掉）+ 增益后峰值 100 > 原图全局峰值 73.6，越过了原图自身的饱和上限。青雾 `rgb(70,196,196)` 的 R 算出 **-9** 被 clamp 成 `rgb(0,174,174)`、S 顶到 1.00，是同一根因的极端表现。叠加 v2 暗色层默认 0，蓝色不被压。

参数参考（深蓝 rgb(65,87,192) 的 C*）：saturation 2.6→91.3 / 2.0→71.2 / 1.8→64.8 / 1.6→57.8 / 1.4→51.3。建议 1.6~1.8；根治要补「色域回缩」（超界时整体缩色度，而不是单通道 clamp）。

## 落地修复：saturation 默认 2.6 → 1.8 + 色域回缩

- `cover_processor.dart`：三处默认值 `saturation = 2.6` → `1.8`；`mesh_flow_widget.dart` 同步（`MeshFlow.saturation` 默认 + 字段文档改成写清净系数公式）。
- 新增 `_gamutFit` / `_gamutFitChannel`：算出浮点 RGB 后若通道越界，**沿亮度轴 anchor 整体收缩色度**（anchor = 该像素零色度时的输出值，即 `((gray-128)*contrast+128)*kBright`），取代原来的逐通道 `clamp`。色相与亮度保住，不再出现 `rgb(0,174,174)` 这种 S=1.0 纯色块。
- 真实管线实测（同一张封面，`processBytes` 导出 32×32 贴图后统计）：

| | 平均 C* | 最大 C* | C*≥65 像素 | 最青像素 |
|---|---|---|---|---|
| 旧 2.6 | 57.0 | 89.4 rgb(42,72,221) | 420/1024 | rgb(3,154,173) |
| 新 1.8+回缩 | 40.9 | 63.4 rgb(55,74,177) | 0/1024 | rgb(31,143,155) |

  原图 32×32 的最高 C* 是 73.6 —— 新版不再越界。
- 新增 `mesh_flow/test/cover_processor_test.dart`（3 条）：深蓝天空色度涨幅 <10% 且色相守恒；青雾最暗通道 >15（不被砸成纯青）；色域外输入（纯青）色相误差 <2°、无通道贴 255。跑测前记得清代理变量。
- **约定**：`saturation` 不是最终倍率，净系数 = `0.5 × saturation × 1.4 × 0.8 = 0.56×saturation`；1.8 ≈ 中性。想留一点提味取 2.0（净 ×1.12），别越过 2.2。


## 浮动 Dock 收起动画：整行上下裁切 → 多图标左移合流成一个

`lib/widgets/floating_dock_bottom_bar.dart`

- 旧实现：Tab 行外套 `ClipRect + Align(heightFactor: 1-t)` 从下往上裁掉，配 `Transform.translate(-24*i*t)`
  的手风琴左推，观感是「整行图标在上下位移」。
- 新实现（`_buildBottomTabs`）：`Stack(clipBehavior: Clip.none)` + 每个图标 `Positioned`，逐图标
  `Transform.translate` 到收起态胶囊那个单图标的中心（左移 + 上移）+ `Transform.scale(1-0.45t)`
  + 各自淡出（当前 Tab 的图标最后淡且画在最上层 = 被它吸收）。展开是同一条轨迹反向播放。
- 合流目标点必须跟着 t 走：`-(进度条高*(1-t) + header高(t)/2)`（相对 tab 行左上角）。写死常数值会差
  约 25px（header 在收起过程中随布局下移 80px），图标会停在空处而不是落进那个图标。
- 外层 `ClipRect` 必须去掉：Align 只压缩布局高度、不裁剪，图标才能平移出这一行；越界由最外层
  `ClipRRect` 兜底。命中区仍靠 `IgnorePointer(ignoring: t > 0.2)`。
- 几何常量收敛到文件头 `_dockHeaderHeight / _dockHeaderPaddingH / _dockCapsuleIconWidth /
  _kDockProgressStripHeight`，header 与 tab 行共用，禁止再写字面量。
- 时机：外层 `TweenAnimationBuilder` 用 `easeOutCubic`（前 1/3 时间走掉大半进度），所以位移
  `converge` 要在 `t/0.62` 内收完、淡出排在 0.30→0.72，否则「刚开始飞就看不见了」。
  微调入口就是这三个数。
- 回归测试：`test/widgets/floating_dock_bottom_bar_test.dart` 新增逐帧采样用例（相邻图标间距收敛到
  <8px、落点与胶囊图标 x 差 <6px、展开后回到原槽位）。

## 暂停后仍满帧渲染 —— 根因是 FFT 输出流与播放态解耦

**现象**：竖屏歌词面板下暂停，DevTools 仍稳定 60fps；每帧 build 0.5–1.3ms、
raster 10–12ms、恒定 14 次 `Canvas::saveLayer`。CPU profile（profile build / Android）
404 samples 里应用代码只占 1.6ms，`dart:ui` 246ms，`audio_core` 17.5ms
（`FftProcessor._groupBins`/`_applySmoothingAndGravity`）。

**根因**：`VisualizerOutputStream` 的 `Timer.periodic(1/targetFrameRate)` 只在
「没有订阅者」时停，与播没播放无关；`VisualizerOutputManager.updatePlaybackState`
是空壳（注释 "For now..."）。暂停后照样每 tick 取采样 → `processRender` 生成新
List（`ValueNotifier` 必触发）→ `_emitFftFrame()`；订阅方（`PlayingEqualizerIcon._onFftFrame`、
`PlaybackVisualizerLayer`）标脏 → `requestVisualUpdate` → `scheduleFrame`。profile 抓到了
`_onFftFrame → ValueNotifier → markNeedsPaint → scheduleFrame` 完整链路。两路 60Hz
同时在跑：`default`(32 组) 与 `mini_player`(128 组，`_initializeMiniPlayerFftStream`)。

**改法（A+B，用户只要求「暂停时平滑落下、不要真实数据」）**：
- `fft_processor.dart`：新增 `decayTowardsSilence(dtSec)`（复用
  `_applySmoothingAndGravity`，target 全零，跳过 `_groupBins`）+ `isSilent`；
  贴地时 `_interpFrom`/`_optimizedState` 一起归零，否则插值留残值（曾卡在 7%）。
- `visualizer_output_stream.dart`：`setPlaying(bool)`；暂停走 `_tickPausedDecay()`
  （衰减 → 渲染 → emit，落到底即 cancel 定时器）；`start()` 去掉
  `if (_isActive) return` 早退——衰减停表后 `_isActive` 仍是 true，早退会导致再也起不来。
- `visualizer_output_manager.dart`：`updatePlaybackState` 真正转发 + 记住 `_isPlaying`，
  新建输出流先对齐（暂停期间新挂的流不会以「播放中」起表）。
- `visualizer_controller.dart`：`updatePlaybackState` 代理 + `_isPlaying` 字段，
  `FftFrame.isPlaying` 不再硬编码 true。
- `audio_service.dart`：`_handlePlayerChanges` 里 play/pause 变化时推送；
  `_updateEffectiveVisualizerState()` 先对齐播放态再 `setEnabled`。
- `playing_equalizer_icon.dart`：`_onFftFrame` 在 `!_isPlaying` 直接 return。
- `playback/playback_visualizer_layer.dart`：`_sameFft()` 逐值去重。
- 回归测试：`test/visualizer_pause_decay_test.dart`（下落单调、落到底停表、恢复能重新起表）。

**遗留**：背景若为「动态流变 / v2」，暂停后仍会 60fps（设计如此，只在退到后台停表）。
改完若还出帧，先查这里。

## Android profile 构建失败：shared_preferences_android「Unresolved reference 'TAG'」

**现象**：`flutter run --profile` 在 `:shared_preferences_android:compileProfileKotlin` 挂掉，
报 `LegacySharedPreferencesPlugin.kt` 里 `TAG` / `SHARED_PREFERENCES_NAME` / `LIST_PREFIX` /
`DOUBLE_PREFIX` / `JSON_LIST_PREFIX` 全部 Unresolved reference；同 package 的**类**（如
`SharedPreferencesApiRegistrar`、`ListEncoder`）却能正常解析。

**根因不是插件代码**（2.5.4 相对 2.5.3 只把 `preferences` 改成 `by lazy`，常量两版完全一致），
是 `android/build.gradle.kts:48` 把非 app 子项目的 buildDir 钉到
`$TMPDIR/vynody_build/${project.name}`——**只有模块名、不含 pub 版本**。
于是 `pub get` 把 2.5.3 换成 2.5.4 后，Kotlin 增量缓存还是 2.5.3 的 ABI 快照，
只有内容变化的 `LegacySharedPreferencesPlugin.kt` 被重编，其余文件只从旧快照查符号
→ 类能查到，**顶层 `const val` 所在的 `*Kt` 门面查不到**。这是鉴别特征。

**判据 / 修法**：
- 秒判：`./gradlew :shared_preferences_android:compileProfileKotlin --rerun-tasks` ——
  全量重编即过，就证明是增量串味，与代码无关。
- 常规清理：`rm -rf $TMPDIR/vynody_build/<模块名>`（`flutter clean` 清不到这里：
  `android/build.gradle.kts:66` 的自定义 clean 只删 `rootProject.layout.buildDirectory`）。
- 结构性防复发（**尚未落地，待用户确认**）：把插件 buildDir 加上 `projectDir` 指纹，
  或让自定义 clean 一并删 `$TMPDIR/vynody_build/*`。
- 触发源：本次 `pubspec.lock` 被整份改写（424 行 `url:` 从 pub.flutter-io.cn 变 pub.dev），
  真实升级只有 8 个包，其中 `shared_preferences_android 2.5.3 → 2.5.4` 是这次爆雷点。

### 回归修复：收起面板时顶行按钮瞬间变回普通 7 按钮

- 现象：竖屏歌词模式控制面板「滑出」的一刻，顶行从「翻译歌词 / 逐字歌词」
  直接跳成普通模式 7 按钮，没有交叉淡出。
- 根因：`buildPortraitControls` 里 `tLyrics` 与 `topButtonsCollapseT` 都门控在
  `_isPortraitLyricsControlsExpanded` 上。收起第一帧它就是 false →
  `tLyrics` 跳 0、`topButtonsCollapseT` 跳 0 → 普通行 opacity 直接 1。
- 修法：门控只认「歌词模式 + 动画进度」——
  `lyricsTopRowActive(v) = effectiveIsLyricsMode && (_isPortraitLyricsControlsExpanded || v > 0)`，
  两个参数都走它。收起时 tLyrics 保持 1.0 直到进度归 0，交叉淡出由
  `topButtonsCollapseT` 单独驱动，与展开方向对称。
- 教训（写进同一类改造的检查项）：**任何 `_isXxx` 布尔开关都不能当动画门控**，
  收起方向它先翻 false、动画值还没走；门控只能看「模式/设置」+「动画值本身」。

### 面板展开/收起时，歌词底部淡出跟着面板一起走

- 现象：面板一上来/一移出，歌词区底部那层淡出是「瞬间切到终位」的。
- 约束：不能让 `bottomSpacerHeight` 逐帧插值（它在 `LyricsPanel.needsRebuild`
  的条件里，逐帧变会每帧重建全部歌词行 = 之前量到的 96ms 根因之一）。
- 做法：给歌词面板开第二条通道，只驱动 `ShaderMask`：
  - `PlaybackHeroCard` 传 `bottomReserveBase`（`widget.lyricsBottomSpacerHeight`，
    收起态基准）+ `bottomReserveDelta`（`progressBarTopFromBottom + 16`，
    门控只看「非横屏 + 设置开关」，**不看** `_isPortraitLyricsControlsExpanded`）
    + `bottomReserveProgress`（同一条 `_portraitControlsExpandAnimation`）。
  - `_LyricsFadeShaderMask`：`reserve = base + delta * t`，
    用 `ListenableBuilder` 只重建 `ShaderMask`；`child` 外面套一层
    `RepaintBoundary`，淡出每帧变化只重做合成、不重栅格化整片歌词。
  - 布局用的 `bottomSpacerHeight` 仍是终值（展开时给全值、收起时归零），不动。
- 数学自检：t=1 → `base+delta` 与改动前完全一致；t=0 → `base`，与收起态一致；
  横屏/设置关时 delta=0 → 恒等旧行为。曲线与面板位移共用同一个
  `CurvedAnimation`，所以淡出边和面板边同步。
- 相关：`lyrics_panel.dart` 的 `needsRebuild` 增加三字段（含 progress 身份比较，
  防止动画对象被换掉后缓存视图还拿着旧的）。

  15:16（提交前）的 profile 里同一路径已占 46.7%。别再把锅甩给那次提交。
- 病因（16:13 profile，507ms / 1470 采样）：
  - `_LayoutBuilderElement._rebuildWithConstraints` 占 **49.3%**（249ms）。
  - 采样栈深度 **22~231 层**，叶子帧全是框架：`framework.dart` 42ms、
    `_compact_hash` 16ms、`collection_patch` 15ms、`object_patch` 13.5ms、
    `basic.dart` 13ms、`semantics.dart` 8.6ms、`gesture_detector` 7.6ms、
    `theme_data` 6.2ms、`ink_well` 5.5ms。
  - app 侧 inclusive 合计只有 **94.5ms**，且**大量落在 `<anonymous closure>`**——
    所以「app 自己代码只占 2.5%」是误读，不是没跑，是帧名匿名。
  - 结论：不是某个函数慢，是「每帧重建的 Element 太多 + 树太深」的摊薄开销。
- 改动（方案 A，低风险两条）：
  1. `lib/widgets/marquee_text.dart` 重写：**去掉 `LayoutBuilder`**。
     宽度改成收缩到文本自身宽度（与 `Text` 一致），对齐交给调用方的 `Align`；
     视口/内容尺寸变化改用 `NotificationListener<ScrollMetricsNotification>`
     （只在 metrics 变化时发，滚动本身不发，不形成回环）。
     `didUpdateWidget` 只比**水平 metrics**（fontSize/weight/style/letterSpacing/
     wordSpacing/fontFamily/textBaseline/locale/fontFamilyFallback/fontFeatures），
     排除 `height`/`color`——转场里 `height` 每帧插值，原来每帧 `jumpTo(0)` +
     cancel/重启 Timer，观感就是跑马灯被反复弹回起点。
     debounce 改成「已有排队就复用」，`_measureAndScroll` 加
     `isScrollingNotifier || _scrollTimer.isActive` 就 return，避免转场中
     每 500ms 打断一次导致跑马灯永远走不出起跑线。
  2. `lib/widgets/playback/playback_track_info.dart`：`GestureDetector` 提到
     `Align` 外面（MarqueeText 不再满宽，右键/长按热区仍要盖住整行）；
     两处 `MarqueeText` 删掉 `alignment:` 入参。
  3. `lib/widgets/playback_hero_card.dart`：`isTransitioningNotifier` 从
     `_buildFullCard` 里每次 build 新建，改成 State 字段
     `_lyricsPanelTransitioning` + `dispose()`；更新时机由 `Future.microtask`
     改 `addPostFrameCallback`。原来转场里每帧换实例 →
     `_LyricsPanelTransitionWrapperState.didUpdateWidget` 每帧重挂 listener、
     把 `_isTransitioning` 重置回 false，再被 microtask 改回 true 触发 setState，
     等于每帧白重建两次。
- 验证：`playback_collapse_button` / `playback_ui_tuning` / `lyrics_panel_logic`
  全过；`playback_screenshot`（竖屏）与 `macos_playback_screenshot`（横屏歌词）
  通过并肉眼确认标题/艺术家居中未裁切；临时的 marquee 布局断言 3 条通过后删除。
- 下一步（未做）：真正瓶颈是 `playback_hero_card.dart` 的
  `TweenAnimationBuilder(tLyrics)` 每帧重建整个卡片 Stack（深 200+ 层 Element

## 设置页 Last.fm 入口在 Android（竖屏）缺失

- 现象：macOS 设置页能看到 Last.fm 分组，Android 看不到。
- 根因是两份手写分组清单不一致，不是平台判断：
  - 横屏/桌面侧栏走 `SettingsSection.sidebarSections`（`settings_section.dart`），**含** `lastFm`；
  - 竖屏首页卡片走 `SettingsPage._buildHomeBody()`（`settings_page.dart` 的 group1~group4），**漏了** `lastFm`。
  macOS 永远横屏走侧栏、安卓手机竖屏走卡片列表，于是表现为「平台差异」。
- 修复：`group2` 末尾补 `SettingsSection.lastFm`（紧跟 acoustid）。`flutter analyze` 通过。
- **约定/隐患**：设置分组清单目前有三份（`sidebarSections`、`_buildHomeBody` 的 group1~4、`settings_search_registry.dart`），新增分组必须三处同步；后续可收敛为 `SettingsSection` 上的分组元数据。
- 另：`LASTFM_SECRET` 只在 `build.yml`（apk/windows/linux/ios 步骤）、`build_dmg.sh`、`build_msix.ps1` 注入。本地 `flutter run` 构建下 `LastFmCredentials.isConfigured == false`，分组内显示「凭据缺失」——这一节仍渲染，与「看不到入口」是两回事。

## 目录页 banner：竖屏非 1:1 封面时列表被顶下去

- 现象：竖屏进含非方形封面的目录，进页瞬间下方列表往下跳一次（约 192dp），
  同时封面从「满幅铺底」变成「模糊背景 + 中间一张内联封面」。
- 定位（`lib/widgets/folder_header_banner.dart`）：
  - `isWideOrSquare = hasImage && (_aspectRatio == null || ratio >= 0.85)` 同一个
    bool 同时管两件事：背景走模糊层（`hasImage && !isWideOrSquare`）与前景多一块
    内联封面（`if (!isWideOrSquare)`）。模糊层是 `Positioned` 铺满、**不改尺寸**；
    真正占位的是前景那块内联封面（`maxHeight: 180` + `bottom: 12`）。
  - `_aspectRatio` 原来只有异步来源（`FileImage.resolve` 解码回调），首帧 null →
    兜底成「宽/方」→ 回调一到翻转分支 → banner 高度瞬增 192dp。banner 是列表
    第一个 `SliverToBoxAdapter`，整张列表被顶下去。
  - 第二跳：内联 `Image` 靠 intrinsic size 撑高，解码前 0、解码后跳 180。
- 修法（已落地）：
  1. `_aspectRatioFromMetadata()` 用 `metadataMap[path].artworkWidth/artworkHeight`
     在 `initState` 同步定比例（`generate_track_artwork` 返回的是**原始封面**宽高，
     `build_thumbnail` 只等比缩放不裁剪），首帧就落对分支；`_aspectRatio` 写入收敛
     到 `_applyAspectRatio()` + `_kAspectRatioTolerance = 0.005`，防亚像素差在 0.85
     阈值附近来回抖。
  2. 内联封面外套 `SizedBox(height: _kPortraitInlineCoverHeight = 180)`，解码前后
     同一足迹。
- 残留（未做）：`hasImage` false→true 那条路径（远程目录封面晚到）仍有 100 占位 →
  180 的 80dp 跳动；无封面目录要保持 100 的观感，所以没把占位一起定高。
