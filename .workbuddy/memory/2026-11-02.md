## 歌词进面板默认查询流程重构

### 起因
审查「进歌词模式」的默认查询链，发现它和「过一会儿重新查询」不等价：
- `setLyricsActive` 直接 `scheduleFetch`，跳过了切歌路径才有的 `tryFastRestoreFromCache`（同一份缓存反而走更慢的路）；
- `fetchAndLog` 在 `duration == null` 时直接放弃，只靠 `retryFetchUntilReady` 12×200ms 硬等，超时无补偿 —— 刚切歌时元数据/时长未回填就永久空白；
- `setLyricsActive` 与 `_updateCurrentMetadata` 尾部双触发，后者 cancel 前者；
- fetch 落地与 `_syncLyricsCacheWatch` 两套合成规则不同（source / syncedLines / hasLyrics / timelineOffset），进入瞬间 A 版、一秒后变 B 版。

### 落地改动
- `LyricsFetchCoordinator.ensureLyricsForSong`：唯一入口，顺序「队列内存 → SQLite 缓存 → 分层查询」，同曲在途幂等（`lyricsFetchInFlightPath`），不再 cancel 重来。
- 缓存查询脱开 duration：`LyricsControllerSupport.lyricsCacheKeyForPath` / `readCachedLyricsRecordByPath` 只按 `normalizeLyricCacheKey(filePath)` 取键；`watchLyricsCacheForSong` 同步改造。
- duration 挂起：`_deferUntilDurationReady` 登记 pending + 15s 兜底；`AudioService._handlePlayerChanges` 首次拿到时长回调 `onSongDurationReady` 续跑。删除 `retryFetchUntilReady`。
- 统一合成：`LyricsControllerSupport.applyLyricsRecordToCurrent`，fetch 与 watch 共用；fetch 落地时先构造 `LyricsCacheRecord` 落库再合成，保证库与展示同源。
- 来源语义：`LyricsCacheSource.fromExternalSourceTag`（`local_lrc`/`remote_server` → `external`，原来会被 default 分支误判成 lrclib）；`result == null` 时不再写空 lyrics（避免把没查到歌词的歌钉死在空状态）。
- 来源优先级唯一：`kLyricsSourcePreferenceOrder`，补回此前漏掉的 `aiKaraoke`；换源弹窗与 watch 选源同源。
- `requeryLyricsForCurrentSong` 清库前抓 `timelineOffset`，重查后回填。

## metadata.db 体积排查与 acoustid_cache 瘦身

### 诊断（实测）
- `metadata.db` 110 MB / page_count 28211 / **freelist 25006 页 = 97.7 MB（88.6%）**；`dbstat` 统计活数据仅约 12.5 MB，副本上 VACUUM 后 12.1 MB。
- 根因：`PRAGMA auto_vacuum = 0`，全仓无任何 VACUUM / incremental_vacuum；SQLite 删除只把页挂 freelist，文件永不缩。
- 峰值来源锁定 `acoustid_cache`：19 行占 2.3 MB，平均 122 KB/行、单行最大 914 KB。旧版四个模型的 `toJson()` 都把该层整棵原始响应重新塞进 `raw`（Result / Recording / ReleaseGroup / Release 各一层 = 同一份数据复制 3~5 层），`AcoustIDRecording.toJson` 还把 `releasegroups` 与 `releaseGroups` 同数组写两遍、`duration`/`length`/`durationMillis` 写三遍。
- 这些 `raw` 在 AcoustID 链路上**从未被读取**：只在 `song_tag_completion_dialog.dart:433-463` 打包进 `MusicBrainzTrackMatch.raw`，而该字段唯一消费者 `musicbrainz_tag_completion_service.dart:102,126` 读的是 MusicBrainz 自己的 `release.raw['media']`。
- 另：同目录 `metadata - 副本.db` 又是 110 MB（待用户自行删除）。

### 落地改动
- `acoustid_service.dart`：四个 `toJson()` 去掉 `raw`，`releasegroups` 只写一份，duration 只写 `durationMillis`，artist 只写字符串（`fromJson` 已兼容）。实测 2280 KB → 150 KB（6.6%），平均 120 KB→7.9 KB，峰值 894→54.8 KB。
- `metadata_drift_database.dart`：
  - `kAcoustIDCacheMaxRows = 500`，`insertOrUpdateAcoustIDCache` 后 `_pruneAcoustIDCache()`（按 updatedAtMillis 淘汰，`limit(-1, offset: 500)`），淘汰后 `PRAGMA incremental_vacuum`。
  - `purgeLegacyAcoustIDCacheRows()`：`DELETE ... WHERE resultsJson LIKE '%"raw":%'`，返回删除行数。
  - beforeOpen 里 purge 命中 > 0 才 `_reclaimDatabaseSpace()`（`PRAGMA auto_vacuum = INCREMENTAL` + `VACUUM`，try/catch 兜住）。
  - `onCreate` 在建表前设 `auto_vacuum = INCREMENTAL`，新库原生支持增量回收。
- 新增 `test/player/acoustid_cache_payload_test.dart` 4 项：不写 raw / 不重复写同名字段 / 体积不随 raw 膨胀 / 往返字段保持。

### 验证
- `flutter analyze lib --no-pub`：两文件无告警。
- `flutter test --no-pub test/player/acoustid_cache_payload_test.dart`：4 passed。

## 续：空洞回收抽成通用机制（修上一版的缺口）

上一版把 VACUUM 挂在「旧格式行被删掉」这个条件上，是巧合不是机制，而且只覆盖了 acoustid，其他表（songs 软删、播放历史、歌词缓存）的 churn 照样留洞。

- 改为 beforeOpen 里无条件调 `_maintainDatabaseSpace()`，三步判定：
  1. `PRAGMA auto_vacuum != 2` → `auto_vacuum = INCREMENTAL` + `VACUUM`（必须同连接，且非空库要靠这次 VACUUM 才落地，一次性成本）；
  2. `PRAGMA freelist_count >= kVacuumFreelistPageThreshold`（4096 页 ≈16 MB）→ 整库 VACUUM；
  3. 其余且 `freelist_count > 0` → `PRAGMA incremental_vacuum` 把文件尾部空闲页还回去。
- `_pruneAcoustIDCache` 淘汰后也走 `_incrementalVacuum()`。
- 删除旧的 `_reclaimDatabaseSpace()`。

### 实测（sqlite3 CLI，115 MB 库副本）
- 必须**同一连接**：`PRAGMA auto_vacuum=INCREMENTAL; VACUUM;` → `auto_vacuum` 变 2；分两次连接执行则一直是 0（VACUUM 那次没设过 pragma）。
- 切完模式后 `DELETE FROM song_play_history` → freelist 89 页；再 `PRAGMA incremental_vacuum` → freelist 0、page_count 3100→3011（文件缩 364 KB）。
- 测试日志已打印 `[Database] VACUUM done: auto_vacuum 0 -> 2`，证明 drift beforeOpen 里 VACUUM 不会因事务报错。

### 顺带发现（未动，待用户定）
- `songs` 有 **975 行 `deletedAt IS NOT NULL`**。所有查询都过滤 `deletedAt IS NULL`，而 `markSongsSeenPresence`（约 2214 行）会 `deletedAt = NULL` 复活、`insertOrUpdateSong` 按 path 直接 upsert —— 所以它们不是墓碑，是纯残留。
- 但**不能直接清**：外接盘未挂载时会整库软删，清了就丢评分/播放次数/波形，插回来要当新歌重扫。要清必须限定「软删时间超过 N 天 + 所属根目录已移除」。
