## 歌词进面板默认查询流程重构

### 起因
审查「进歌词模式」的默认查询链，发现它和「过一会儿重新查询」不等价：
- `setLyricsActive` 直接 `scheduleFetch`，跳过了切歌路径才有的 `tryFastRestoreFromCache`（同一份缓存反而走更慢的路）；
- `fetchAndLog` 在 `duration == null` 时直接放弃，只靠 `retryFetchUntilReady` 12×200ms 硬等，超时无补偿 —— 刚切歌时元数据/时长未回填就永久空白；
- `setLyricsActive` 与 `_updateCurrentMetadata` 尾部双触发，后者 cancel 前者；
- fetch 落地与 `_syncLyricsCacheWatch` 两套合成规则不同（source / syncedLines / hasLyrics / timelineOffset），进入瞬间 A 版、一秒后变 B 版。

### 落地改动
- `LyricsFetchCoordinator.ensureLyricsForSong`：唯一入口，顺序「队列内存 → SQLite 缓存 → 分层查询」，同曲在途幂等（`lyricsFetchInFlightPath`），不再 cancel 重来。
- 缓存查询脱开 duration：`LyricsControllerSupport.lyricsCacheKeyForPath` / `readCachedLyricsRecordByPath` 只按 `normalizeLyricCacheKey(filePath)` 取键；`watchLyricsCacheForSong` 同步改造。
- duration 挂起：`_deferUntilDurationReady` 登记 pending + 15s 兜底；`AudioService._handlePlayerChanges` 首次拿到时长回调 `onSongDurationReady` 续跑。删除 `retryFetchUntilReady`。
- 统一合成：`LyricsControllerSupport.applyLyricsRecordToCurrent`，fetch 与 watch 共用；fetch 落地时先构造 `LyricsCacheRecord` 落库再合成，保证库与展示同源。
- 来源语义：`LyricsCacheSource.fromExternalSourceTag`（`local_lrc`/`remote_server` → `external`，原来会被 default 分支误判成 lrclib）；`result == null` 时不再写空 lyrics（避免把没查到歌词的歌钉死在空状态）。
- 来源优先级唯一：`kLyricsSourcePreferenceOrder`，补回此前漏掉的 `aiKaraoke`；换源弹窗与 watch 选源同源。
- `requeryLyricsForCurrentSong` 清库前抓 `timelineOffset`，重查后回填。
