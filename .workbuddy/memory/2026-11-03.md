## 修复：翻译歌词流式生成时，每出一行所有已生成译文行重播进入动画

**现象**：AI 歌词翻译边流式产出边显示时，每来一行新译文，之前已经淡入完毕的所有译文行
都会重新播一次 `AppleLyricTranslationFadeIn` 的淡入＋上浮。

**定位**（临时探针 `[LyricsFadeProbe]`，跑一遍复现后已全部删除）：run.log 里
`translatedLines=null` 的帧与 `[LyricsController] lyrics cache watch applied ...
translationsFromDB=[] (recordsCount=0)` 一一对应，紧接着就是一批 `trans init idx=0..N`
＋同批 `dispose`。即整份译文在某一帧被清空，下一帧又被流式同步填回来 → 每行淡入 State
重建 → 动画重播。链条：

1. 每个 chunk → `_syncTranslatedLyricsToSong` → `unawaited(_saveTranslatedLyricsToDatabase)`
2. 写库走 `insertOrUpdateLyricsTranslationCache` 的**「先按 (cacheKey, languageCode) 删除、
   再 insert」**
3. 删与插之间的空窗里 `watchLyricsTranslationCaches()` 给订阅方吐一份 **空列表**
4. `_syncLyricsCacheWatch` → `applyLyricsRecordToCurrent(translations: {})` 整份覆盖内存译文
5. 下一帧 chunk 又把译文填回来 → 所有行 State 重新 init

顺带查出两个真 bug：

- `insertOnConflictUpdate()` 生成的冲突目标是主键 `id`，命中不了 `UNIQUE(cacheKey, languageCode)`；
  并发/交错写入直接 `SqliteException(2067) UNIQUE constraint failed`（日志里反复出现）。
- 流式快照本身偶尔比上一帧少一行（`LyricsAiTranslationTextHelper.visibleTranslationText`
  按「去掉末尾半行」裁切 + 空行重排），那一行的译文会消失一帧再回来，同样触发单行重播。

**改动**：

- `metadata_drift_database.dart::insertOrUpdateLyricsTranslationCache`：改成一条原子
  `insert(companion, onConflict: DoUpdate(..., target: [cacheKey, languageCode]))`，
  没有 delete 空窗，也没有 UNIQUE 冲突。
- `lyrics_controller_utils.dart::applyLyricsRecordToCurrent`：新增
  `_mergeTranslationsWithoutRegression` —— 按语言取「非空行数更多」的一方；翻译进行中
  DB 快照缺这门语言时沿用内存版本。
- `lyrics_controller_translation.dart::_syncTranslatedLyricsToSong`：流式阶段
  (`bumpLayoutRevision == false`) 用 `_mergeStreamingTranslatedLines` 把「新快照变空但上一帧
  有内容」的行补回旧值；收尾那次仍整份覆盖。

**回归**：`test/player/lyrics_translation_cache_watch_test.dart`
（① watch 流一旦有过数据就不得再回到空；② 并发写不抛 UNIQUE、后写者生效）。
已验证这两条在旧实现下**都会失败**，新实现下通过。`flutter analyze` 干净；
`music_lyric` / `lyrics_entry_flow` / `lyrics_panel_logic` 全绿。

**环境备注**：跑 `flutter test` 会让 `pubspec.lock` 的 flutter_taglib 从 `path:` 翻成
override 里的 `git ref: master`（已 `git checkout` 还原，与本次修改无关）。

## 翻译行「跳行时重播淡入动画」—— 行包装层缺 key 稳定性

**现象（修复上一轮之后的新报障）**：翻译流式生成中，播放推进到下一行时，已经出现的
译文行会重新播一次淡入/上浮。

**定位依据**：旧探针日志计数 `stagger init = 56`、`stagger restart = 0`、`line init = 0`。
restart 为 0 说明不是滚动补偿重启动画，而是 **Staggered 的 State 被反复重新 init**
（重建），连带行内 `AppleLyricTranslationFadeIn` 丢 State。`line init = 0` 说明翻译期间
`isGenerationBusy` 恒 false（`AppleLyricLineFadeIn` 从未实例化），所以 `isGenerating`
那条分支不是本次元凶。

**根因**：`lyrics_panel_views.dart` 行构建里

```dart
final bool isInStaggerRange = !widget.isGenerating && widget.isFocusMode &&
    index >= widget.firstVisibleIndex - 10 && index <= widget.firstVisibleIndex + 30;
if (isInStaggerRange) { resultWidget = StaggeredAppleLyricsScrollWrapper(...); }
else { resultWidget = contentWidget; }
```

窗口边界跟着 `firstVisibleIndex` 走，跳行/滚动时边界平移 → 进出窗口的行子树根类型变化
→ 整行 Element 重建 → 译文重播。（Apple 歌词 `_isFocusMode` 默认 true，所以常态触发。）

**修法**：

- 行构建：`StaggeredAppleLyricsScrollWrapper` **常驻**，范围只作为 `enabled` 参数。
- 组件：新增 `enabled`；`AnimationController` 惰性创建，`enabled=false` 时
  `_releaseController()` 释放 ticker 只留空 State；`enabled` 由 false→true 时补建并
  `_startAnimation()`。
- `SingleTickerProviderStateMixin` 必须换 `TickerProviderStateMixin`（惰性重建会出现
  第二个 ticker，否则 assert「multiple tickers were created」）。
- build 结构必须恒定 `ExcludeSemantics > AnimatedBuilder > Transform > child`：未启用时
  用 `AlwaysStoppedAnimation(0.0)` 占位，**禁**在 offset==0 时省掉 Transform —— 少一层
  就是 child 换父级，照样重建（第一版就踩了，测试直接抓到）。

**回归**：`test/widgets/lyrics_staggered_wrapper_test.dart`（① enabled 反复翻转时探针
initState 计数恒为 1；② enabled=false 时不产生任何位移）。
`flutter analyze` 仅剩原有 5 条 `dead_code`；`lyrics_panel_logic` / `music_lyric` /
`lyrics_translation_cache_watch` 合计 17 个测试全绿。

## 译文「跳行重播」真凶：焦点模糊层的类型切换

**现象**：行包装层常驻之后问题仍在。用户点名两句（index 9 `We don't talk much, not anymore`、
index 10 `Broken bottles and slammin' doors`）——播到下一行时该行译文又淡入一次。

**日志判读（`[Tprobe]`）**：

- `view-init` 只有 1 次 → view State 一直存活。
- 69 次 `stagger-init` 全部落在 270-406 这一连续段 → 是**首次构建**，不是重建。所以
  上一轮的常驻修复本身是对的，本次不是它。
- 关键一行：`trans-init idx=9 active=9 animate=true size=true`，而它**前面没有任何
  `slot idx=9` 翻转** → 译文内容没变、行结构没变，纯粹是行内子树被重建。
- 同时 `trans-init idx=8 active=9 size=false`（模糊从 0 → 正数，size=false 所以不播）。
- `trans-animate true->false` 69 次 = 行总数，翻译结束那一帧所有行各报一次，属正常。

**根因**：`lyrics_panel_views.dart` 逐行模糊包装

```dart
builder: (context, blurSigma, child) {
  if (blurSigma <= 0.0) return child!;          // 裸 child
  return ImageFiltered(imageFilter: ..., child: child);  // 多一层
}
```

`targetBlur` 依赖 `|index - activeIndex|`。跳行时新当前行从「正数」动画到 0、上一行从
0 动画到正数，**只要越过 0 这一步，父级 widget 类型就变了**（`ImageFiltered` ↔ 裸 child）
→ 整行 Element 重建 → `AppleLyricTranslationFadeIn` 丢 State → 重播。这也解释了为什么
每次跳行只重建 1~2 行（跨 0 边界的那两行），以及屏幕外行进入视口时也会重建（blur 0 → 正数）。

**修法**：builder 恒定返回 `ImageFiltered`（sigma 为 0 也保留该层）。

**验证**：新增 `test/widgets/lyrics_line_blur_stability_test.dart`——直接构造
`LyricsPanelTimedLyricsView`（activeIndex 1 → 2），用 `identical(state_before, state_after)`
断言第 2 行译文 State 未重建。已用旧写法回跑确认**会失败**（日志复现
`trans-init idx=2 active=1` → `trans-init idx=2 active=2`），新写法通过。
`flutter analyze` 仍只剩原有 5 条 `dead_code`，5 个文件 18 个测试全绿。

**探针保留**：`lyrics_panel_views.dart` 里 `[Tprobe]` 打点先不删，等用户复现确认后再清。

**收尾**：用户确认已修好。已清掉全部 `[Tprobe]` 打点与配套的 `_probeSlotHadText` /
`_probeActive` / `_probeLang` 字段，`flutter analyze` 只剩原有 5 条 `dead_code`；
`lyrics_line_blur_stability` / `lyrics_staggered_wrapper` / `lyrics_panel_logic` /
`music_lyric` / `lyrics_translation_cache_watch` / `lyrics_entry_flow` 共 25 个测试全绿。

## 播放页底部 Dock 高亮跟随底层 Tab

**现象**：进入播放页后底部导航所有图标都是未选中态（灰 / 白 45%），看不出自己在哪个上下文。

**根因**：播放页抽屉里那个 `FloatingDockBottomBar` 实例写死 `currentIndex: 1`
（`lib/pages/main_layout.dart`），而 `tabs` 只含 `0/2/3/4/5` —— index 1 就是播放页自己、
不占导航位，于是 `tabs.indexWhere` 返回 -1，`selectedPos >= 0` 判假，全部走未选中分支。

**修**：该处改为 `currentIndex: _currentIndex`。播放页是覆盖在底层 Tab 之上的抽屉，
`_expandPlayback()` 不碰 `_currentIndex`，且 `_currentIndex` 永远不是 1
（`initialBaseIndex = widget.initialIndex == 1 ? 0 : widget.initialIndex`），
所以它天然就是「当前路由位置」。

**副作用确认**：`currentTab`（收起态胶囊图标）在播放页用不到（`hideMiniPlayer: true`
→ `showMini == false`）；点已高亮那个 tab 会先 `_collapsePlayback()` 再 `_selectTab`
因 index 相同直接 return，行为正确。

## 切歌链路资源审计（只读，未改代码）

链路：`playAtIndex/next/previous` → `PlaylistController.playByIndex/_reconcile` →
`AudioCoreController.loadTrack`（Apple scoped access → `performTransition` → engine.load →
`visualizer.resetState` → Android 200ms 后 `equalizer.reapply`）→
`AudioService._handlePlayerChanges` → `_syncCurrentPlaybackSong`
（`_updateCurrentMetadata` + `_refreshCurrentWaveform` + lyrics `clearState`）。

判定为「确实会涨」的三处：

1. 队列项长期持有整张封面字节：`_replaceQueueSongsByPath` → `replaceTrack` 把 `MusicFile`
   （含未缩放的 `artworkBytes`）塞进 `AudioTrack.metadata['musicFile']`。
   `queue_background_processor.dart:110-122` 的「清空非当前曲封面」只改局部 `_queue` 副本，
   回写又被 `_sameQueueMetadata`（不比较 artworkBytes）挡掉 → 实际是死代码。
2. Apple 安全作用域只开不关（仅播放路径）：`VisualizerPlayerController` 三处、
   `rust_audio_engine.dart` 三处、`audio_service.dart` 三处都在 `beginScopedAccess`，
   全都没有配对的 `endScopedAccess`，同一首歌一次切换 retain 2~3 次。
   **勘误**：并不是「Dart 侧全仓无 end」——`scanner_service` 四处、`sharing_service`
   一处都是成对的，问题只在播放路径。目录书签按 key 去重只涨计数（无实质泄漏）；
   单文件书签（外部打开 / iOS open-in）每首真开 2~3 个 scope 永不 stop。
   `RustAudioEngine` 里那三处是纯重复，修的时候先删掉它们。
3. AI 歌词生成：`_context.lyricsAiCancelToken = cancelToken` 直接覆盖旧 token 不 cancel，
   切歌不中断上传/转码/流式响应。

次要：远程每次 resolve 新建 Subsonic/Jellyfin/WebDavClient（各自 Dio，从不 close，
Jellyfin 每次重新 authenticate）；`_updateCurrentMetadata` 的封面水合是无取消的 unawaited，
快速切歌会并行解码多张封面；`_dispose()` 漏了 Android/Darwin integration 的 dispose。
附带（非切歌）：`folder_header_banner.dart:160-188` 的 `ImageStreamListener` 从不 remove。


## 修复：队列项长期持有二进制列（问题①，已落地）

做法是「写入侧收口 + 切歌清理」，没有改队列 track 的数据结构。
`artworkBytes` 和 `waveformBlob` 走**同一套**判定。

- `audio_service.dart` 新增 `_queueTrackForSong(song)`（无参）：队列里只有当前曲能带
  `artworkBytes` / `waveformBlob`，其余走 `copyWith(artworkBytes: null, waveformBlob: null)`。
  四个 `replaceTrack(_audioTrackForSong(...))` 调用点（`_updateSongInPlaylist` /
  `setSongMissingStateByPath` / `_replaceQueueSongsByPath` / `_flushQueueMetadataWriteBack`）
  全部改走它。`_audioTrackForSong` 保持原样（`setQueue` 那处还需要它）。
- 新增 `static shouldStripQueueBinaryBlobs({songPath, keepPath})` 作为唯一判定，
  顺便解决一个坑：`AudioTrack.uri` 存的是 iOS/macOS 沙盒解析后的路径，
  `MusicFile.path` 可能还是旧容器 UUID，直接 `==` 会把当前曲误判成非当前曲、
  连它的封面和波形一起剥掉。判定里用 `ScannerPathUtils.resolveIosSandboxPath`
  兜底（带 `_resolutionCache`，不打 IO）。
- 新增 `_releaseStaleQueueBlobs()`（**无参**），在 `_syncCurrentPlaybackSong`
  的 `_trackedPlaybackSongPath != song.path` 分支里调。「保留谁」只由
  `playlist.currentTrack` 决定，不吃调用方入参 —— `_syncCurrentPlaybackSong`
  有 8 个调用点，不能保证入参就是当前曲，传错会清掉正在播的那首。
  `currentTrack == null` 直接 return（那是队列清空/还没起播，不是切歌）。
  遍历前先收集成 list 再 replace，因为 `replaceTrack` 会原地改写
  `_activePlaylistTracks`。
- 删掉 `queue_background_processor.dart` 里那段死代码（原 109-125）：
  它改的是 `AudioService.queue` getter 每次新建的局部副本，`onChanged` 只发通知、
  从不写回 playlist。连同 `artworkPriorityPaths` 一并删除，原 127 行的触发条件
  简化为 `priorityIndices.isNotEmpty && waveformMemoryPaths.isNotEmpty`。
- 回归测试 `test/player/audio/queue_binary_blob_release_test.dart`（7 条）：
  5 条测 `shouldStripQueueBinaryBlobs` 的边界，2 条锁 `MusicFile.copyWith`
  的 freezed sentinel —— 一旦有人把 `MusicFile` 改成手写 copyWith，
  `copyWith(x: null)` 会静默保留旧值、整套收口失效而不报错，那两条就是哨兵。
  `test/player/audio/` 全量 31 条通过。

**量化结论（重要，别按「几十 KB」估）**：`waveformChunks` 默认 100，
`waveformBlob` 是 Float32 → **每首只有 400 字节**，1000 首才 400KB。
它本身不是内存问题，清它换来的是「队列不存二进制」的一致约束
（`scanner_tree_builder` / `scanner_metadata_store` 早就是这个约定）。
真正的大头是 `artworkBytes`（100KB~3MB/首）。

**副作用确认**：
- 非当前曲 `artworkBytes` 变 null 后，`getCachedArtwork` 的第三级（在队列里找别曲
  bytes）实际失效；消费方都有降级 —— `SongThumbnail` 走 `thumbnailPath`，
  `cover_carousel` 走 `ArtworkResolver.resolveForCarousel`，`_artworkCache`（有界 200）仍在。
- 非当前曲 `waveformBlob` 变 null 后没有读者损失：`MusicFile.waveform` 只在
  `playback_progress_section.dart:214/555` 被读，都是 `currentMusic?.waveform`。
  切回已播过的歌不会重新解码 —— `getWaveformData` 首次算完就写 DB，
  回来时 `streamWaveform` 命中 DB 立即 yield；外加 `MusicFile._waveformMemoryCache`
  8 条兜住最近 8 首的即时渲染。只有切回第 9 首以前才会有一帧空窗。
- `queue_background_processor` 的 `needsDbSync`（`inWaveform && song.waveformBlob == null`）
  现在对当前曲前后各一首恒为 true，每轮最多多 6 次 `db.getSongMetadata`。
  对当前曲是好事（切歌后立刻从 DB 恢复 blob，不必等 `_refreshCurrentWaveform`）。
- `_sameQueueMetadata` 不需要加 artworkBytes / waveformBlob 比较，
  清理不走 `_flushQueueMetadataWriteBack` 那条路径。

待办：Apple scope（问题②）按「收敛 begin 到唯一入口 + 成对 end」修，用户测完①再动。
## 移除：无效的封面「预处理队列」（Phase 1.5，已落地）

用户以为「当前/上一首/下一首封面会被预解码进内存」这个设计在起作用，核查后发现
**预热 100% 不命中**，已整条删除。

**为什么无效**（决定性）：预热用 `ResizeImage(FileImage, width: 800, height: 800)`，
UI 用 `Image.file(cacheWidth: W)` → `ResizeImage(FileImage, width: W, height: null)`。
`ResizeImage.==` 逐字段比较（provider/width/height/allowUpscaling/policy），
height `800` 与 `null` 永不相等 → 两条 ImageCache 条目，永远 miss。
`W` 来自 `PlaybackArtworkTuning.calculateCoverCacheWidth()`（桌面 800~2048 按 400 分桶、
移动端 400~1200），所以连 width 也只有低配机型恰好等于 800。
附带问题：源路径 `existing?.artworkPath ?? existing?.thumbnailPath` 会拿缩略图当 HD 封面；
`provider.resolve()` 不带 listener，条目是普通 LRU，不保证切歌时还在。

**为什么不补 key 而是直接删**：`CoverCarousel._buildItems`（cover_carousel.dart:390-396）
本来就只构建 `center / center-1 / center+1` 三张，且用正确的 `W`——
播放页一打开，这三张已经在 ImageCache 里。也就是说预热是重复劳动，
每张还白占约 2.56MB（800×800 RGBA）并挤掉真正的热点条目。

**改动**：
- `playback_queue_processor.dart`：删 `processQueue` 的 `onHdArtworkLoaded` 参数 +
  整个 Phase 1.5（原 266-301，含 3 次串行 `db.getSongMetadata`），原位留注释说明原因。
- `queue_background_processor.dart`：删 `onHdArtworkLoaded` 回调整段（原 298-348，
  含预热与「写 `queue[i].artworkPath` + `onChanged()`」那段——后者也是死代码：
  `onChanged` 传的是 `notifyListeners`，改的是 `AudioService.queue` getter 新建的
  局部副本，UI 重建时读的是 playlist track），并移除只为它存在的 `import 'dart:io';`。
- 调用方只有 `queue_background_processor` 一处，两个测试文件调 `processQueue` 都没传该参数。

**验证**：`flutter analyze` 两文件 0 问题；`test/player/audio/` 全量 31 条通过。

**日后想真做事的话**（如果实测从迷你播放器点开播放页有解码空窗）：
在 `CoverCarousel` 里对 `center±2` 用 `precacheImage(ResizeImage(FileImage, width: finalCacheWidth), context)`，
复用 `calculateCoverCacheWidth` 这个唯一入口，key 天然一致。**不要**在播放逻辑里反向依赖界面尺寸。
