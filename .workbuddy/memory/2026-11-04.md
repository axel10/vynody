  `xcrun swiftc -typecheck` 通过。

  参数（`readAccessHolder`，缺省走 `defaultAccessHolder`）。

  从 `audio_core.dart` 导出；`AudioEngine` 接口 / Rust / Android 引擎 /
  `AudioCoreController` 的 begin/end 全部加可选 `holder`。
- 打标：scanner（`scanner_service.dart` 4 处）、playback（`rust_audio_engine` 3 处、
  `visualizer_player_controller` 4 处、`audio_service` 3 处）、sharing（`sharing_service`

  finally 只 end 真正拿到的那一条。

## Apple 安全作用域统一性审计（回答用户提问）

- 原生侧统一：`SecurityScopedFileAccessCoordinator`（唯一 `fileAccess` 实例）+
  按 `(scope key, holder)` 分账；暴露面只有 `audio_core.player` 的 6 个 method。
- Dart 侧不统一：4 个入口并存 —— `rust_audio_engine._appleChannel`、
  `visualizer_player_controller` 包装、`sharing_service.dart:454`、
  `audio_converter.dart:991`、`file_selector_helper.dart:56` 各自声明
  `MethodChannel('audio_core.player')` 并各自吞异常。
- playback holder 全仓无 `endScopedAccess`（`lib/` 只有 scanner / sharing 有），
  且 app→controller→engine 三层各 begin 一次 → 单曲 +3、永不回收。
- `getAudioPcm` / `getAudioPcmChannelCount` 走 default holder，与 playback 分账错位。
- `sharing_service.dart:1190-1200` 接受入站请求时 begin 后无 end（每次 +1）。
- `flutter_taglib/ios/.../FlutterTaglibPlugin.swift` 自带 `activeUrls` + 私有
  bookmark store，并用 `options: []` 往 `audio_core.securityScopedBookmarks`
  写非 scope bookmark；其 `startAccessingDirectory/commitPickedFile` 在 Dart 侧
  无调用点（死代码），一旦启用会污染协调器缓存。
- `MEMORY.md` 因超注入上限被截断 → 已拆出 `MEMORY-ui.md`（缩放/歌词/封面/详情），
  主文件 14.8KB → 6.7KB。
