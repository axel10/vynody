## 修复：MusicBrainz 标签补全后播放页封面不更新

### 根因

- 磁盘封面按**封面内容 md5** 命名（`audio_core/rust/src/api/simple/metadata.rs` `generate_track_artwork`），
  换封面天然换文件名 → 列表/队列页的 `SongThumbnail` 读 `artworkPath`/`thumbnailPath`，因此正常刷新。
- `AudioService._artworkCache` 以**曲目路径**为 key，写入后从不过期。
  `CoverCarousel._buildCoverImage` / `_loadArtworkAsync` 的第一优先级就是它
  （`lib/widgets/cover_carousel.dart:848`、`610`），于是播放页永远停在旧图。
- `applyUpdatedSongMetadata` 只调了 `clearAudioDetailsCache`（管时长/码率），没碰封面缓存。
- `getCachedArtwork` 的「字节更大者更清晰」兜底救不回来：它要求权威值**更大**，
  而网络补全封面通常比播放时解码的内嵌原图小。
- 次生问题：`_CoverItem.didUpdateWidget` 命中缓存后会把旧字节再 `setCachedArtwork` 写回，
  等于给旧封面续命；且 `_hasLoadedHighRes` 拦住重新解析。

### 改法

- 新增 `AudioService.syncArtworkCacheAfterReplace()`（静态纯函数，操作 `Map<String, Uint8List>`，
  便于单测）+ `invalidateCachedArtwork()`。同时清 path 与其 URL-decode 变体两个槽位。
- `applyUpdatedSongMetadata` 在**队列替换之后**调用它（顺序要紧：`getCachedArtwork`
  的「更大者更清晰」会拿 `currentMusic.artworkBytes` 覆盖缓存，先同步会留出旧大图盖新图的窗口）。
  仅在 `artworkBytes != null` 时调用：纯文本编辑保留缓存，空字节 = 清封面。
- `_CoverItem.didUpdateWidget` 增加 `artworkIdentityChanged` 判据（`artworkPath`/`thumbnailPath` 变化）
  → 重置 `_artworkBytes`/`_hasLoadedHighRes`。只认路径类字段，不认 `artworkBytes`
  （同图缩略图/原图两种规格，起播预热写原图不该触发重置，否则封面会闪）。

### 测试

`test/player/audio/cached_artwork_test.dart` 新增两组：
- 「封面被替换后内存缓存必须失效」：小图覆盖大图、null/空字节清理、编码路径双槽位、容量上限。
- 「applyUpdatedSongMetadata 的封面缓存契约」：读 `audio_service.dart` 源码断言函数体内仍有
  `syncArtworkCacheAfterReplace(`。因为 `AudioService` 是 Riverpod Notifier + 依赖 Rust 内核，
  单测起不了实例，只能锁源码契约。

## 追加：编辑标签的「保存到 App」按钮收敛（同日第三轮）

### 结论

不能直接删。`flutter_taglib` 覆盖的是 TagLib 有 `save()` 的容器，扫描清单里仍有
5 种 TagLib 连解析器都没有：`.aac`（裸 ADTS）、`.caf`、`.dff`、`.mid`/`.midi`（MOD 只读属性）。
删掉入口后这些文件完全无法改标签；另外写回会因占用 / 只读挂载 / SAF 只读授权在运行期失败，
那时 `saveSelectedSongMetadata` 直接 `return null`（连 DB 都不写），没有退路就保存不了。

### 真正该修的是清单

`writableMetadataExtensions` 一直停在 `mp3/m4a/mp4/flac/wav`，而 `taglib_config.h` 已开
`VORBIS / APE / ASF / DSF / MATROSKA / RIFF / TRUEAUDIO / MP4`。于是 ogg/opus/aiff/ape/dsf/webm
明明能写却被挡在门外（按钮置灰、右键「保存到文件」点不动）。

### 改动

- 清单补全：`mp3 m4a m4b mp4 alac flac ogg opus wav aif aiff ape dsf webm`；删掉从未被引用的
  `unsupportedMetadataExtensions`（`{'.ogg','.opus'}` 那个假清单）。
- 编辑弹窗：两个按钮 → 一个「保存」。`_save()` 不再收 `writeToFile`，能写就写回。
- `saveSelectedSongMetadata` 返回 `SelectedMetadataSaveResult`（`wroteToFile` + `TagWriteFallback`），
  新增 `fallbackToAppOnWriteFailure`：写失败时不清 `isAppModified`、只落库，之后还能「保存到文件」重试。
  降级路径 `saveLarge` 也要为 true，否则文件里没有新封面、App 里只有缩略图，播放页大封面会糊。
- 结果类 `SongTagEditResult` 改成 counts（`writtenToFileCount`/`appOnlyCount`），
  `savedToSourceFile` 变 getter；提示统一 `songTagEditResultMessage()`。
  修掉老 bug：批量里混着不可写格式时，静默降级成只存 App 却仍报「已保存到源文件和 App」。
- l10n：新增 `tagSavePartiallyWritten(written, appOnly)`；`editSongTagsDescription`、
  `batchEditSongTagsDescription`、`unsupportedFormat`、`unsupportedFormatSingle` 去掉
  「可以只保存到 App」「(OGG/Opus)」等过时说法，9 个 arb + `flutter gen-l10n`。

### 测试

## 安卓白屏：UI isolate 出帧被饿死（P0+P1 已修）

**现象**：mac 推送歌词到安卓，同步完成后安卓白屏；音频正常播放、无异常日志、
返回键只退到后台、DevTools 帧不再渲染、只能杀进程。

**判据**：`launch_background.xml` 是纯白 `@android:color/white`，所以白屏 =
Flutter 没盖上图层，不是渲染出错（渲染异常会走 `FlutterError.onError` / release 灰屏）。

**CPU profile（2.15s / 269 samples）根分支分布**：

| 分支 | 占比 |
|---|---|
| `_Timer._handleMessage → _runTimers` | 68.4% |
| `_microtaskLoop` | 23% |
| `_dispatchPlatformMessage`（vsync 走这条） | 6.7% |

热点链：`_onRenderTick`(60Hz) → `_advanceLocalPosition` → `player.updatePosition`
→ `notifyListeners` → `AudioService._handlePlayerChanges`。其中
`AudioService.queue` 240ms（11%，队列全量 map+toList）、
`_updateLastFmTracking` 里的 `ref.read` 184ms（8.5%）、`updateTimeline` ×4 每帧打平台通道。

**改动**（只动 `lib/player/audio/audio_service.dart`）：
- `_updatePlaybackSessionAutoSaveTimer`：`_queue.isNotEmpty` →
  `_player.playlist.items.isNotEmpty`（O(1)，不再每帧建全量列表）。
- `_updateLastFmTracking`：缓存 `LastFmScrobbleService`（`_lastFmScrobbleServiceCache`），
  热路径不再 `ref.read`；`_dispose` 里置空。
- `_handlePlayerChanges`：新增 `_heavyPlayerSyncInterval`(200ms) 闸。
  平台 `updateTimeline` / Last.fm 判定 / 歌词补抓 / autoSave 重估按闸跑；
  `updatePlaybackStatus` 与 autoSave 重估在播放态变化时立即执行（不能等闸，
  否则暂停后定时器停不下来）。
- 新增 `_logSlowPlayerChanges`：单次回调 >8ms 打印告警，每秒最多一条。

### 追加：白屏真因是路由被弹空，不是掉帧（上面那批节流改动仍保留，但不是病根）

**现象**：Mac 推歌词到安卓 → 传输完瞬间整页下滑、白屏；音乐照放；返回键退到后台；
只能杀进程重开。日志里只有一条
`[NavTrace] MainLayout.PopScope invoked: didPop=true`。

**真因**：`lan_sync_dialogs.dart` 进度对话框收尾时**第二次 pop**，弹掉了主路由。
- `showDialog()` 返回的 future 是路由的 `popped`，`Route.didPop → didComplete`
  **在 pop 那一刻**就完成，不等退场动画。原注释「whenComplete 要等退场动画」
  是错的。
- 于是 `whenComplete` 里复位 `_closing=false / _progressDialogOpen=false` 时，
  对话框 widget 还挂在树上跑退场动画；它的 `build` 因 `progress == null`
  又排了一次 post-frame「自己退栈」，`_closing` 已被清 → 直接
  `Navigator.of(context).pop()`。
- `Navigator.pop()` 弹的是**栈顶**；对话框那条路由已处于 `pop` 态（`isPresent`
  为假），被弹掉的就是下面的 `MainLayout` → 导航器变空 → 只剩窗口底色（白）
  → 帧无事可画（DevTools 显示停止出帧）→ 返回键直接退出。
- `didPop=true` 只在同步收尾后出现，用户真实返回键那次是 `didPop=false`，
  这是判据。

**修法**（`lib/dialogs/lan_sync_dialogs.dart`）：
1. 关闭一律按**路由身份**退栈：`_dismissRoute(route)` ——
   `isActive` 为假直接 no-op；`isCurrent` 才 `pop()`，否则 `removeRoute(route)`。
   永远不碰栈顶。
2. 状态复位从 `whenComplete` 挪到对话框自己的 `dispose()`（退场动画跑完、overlay
   项移除），`_closing` 标志整个删掉。
3. `showLanSyncProgressDialog` 的「已开着」判定改为
   `_progressDialogOpen && (existing == null || existing.isActive)`，否则连着两次
   同步时第二次会被上一个对话框的残余状态挡掉。
4. `main_layout.dart` 的 PopScope 在 `didPop=true` 时打一条 `StackTrace.current`，
   以后再犯直接指认凶手。

**测试**：`test/player/lan_sync_stage3_test.dart` 新增两例（先 hide 再自退栈不能弹
主页面 / 连续两次同步不能被残余状态挡掉）。已用 `git show HEAD:` 还原旧代码验证过
两例在旧代码上确实失败（`Found 0 widgets with text "open"`），修复后 66 passed。

## 审计：Android 系统媒体库目录代表封面按标题而非音轨号（未改代码）

用户报的现象：目录代表封面选曲只按标题排，没优先用 `trackNumber`；且**仅限 Android
系统媒体库**，用户自己添加的根目录正常。核查结论「是」，但根因不在排序器：

- `FolderCoverResolver.compareSongsForFolderCover`（`scanner/folder_cover_resolver.dart:84-106`）
  本身就是 `trackNumber > 0` 升序 → 标题 → 文件名；4 个调用点（含 isolate 版
  `computeAllFolderCoversInBackground`）全用它，`folder_cover_resolver_test.dart` 有单测。
  自己添加的根目录走 `musicFileFromSongMetadata`（`scanner_tree_builder.dart:314`）带音轨号，正常。
- Android 断链四处：`MyExoplayerPlugin.kt:1001-1013` 的 MediaStore projection 没有
  `TRACK` / `CD_TRACK_NUMBER`；`audio_core/lib/src/android_media_library.dart:4-29`
  的 `AndroidMediaLibraryEntry` 无 `trackNumber` 字段；
  `scanner_tree_builder.dart:467` 的 `musicFileFromAndroidEntry` 只取
  `resolvedMetadata?.trackNumber`（同函数 title/artist/album/duration 都有 `?? entry.xxx` 兜底）；
  `scanner_service.dart:2317-2327` 建树时 `getSongMetadataByPaths()` 为空（后台解析 `:2347`
  才启动），且 `:2923-2931` 后台只写 DB + `_metadataStore`、**不回写** `folder.files`，
  `:1248` 刷封面直接把内存树传进 isolate。冷启动 `:2514` 从 DB 建树本有音轨号，
  但随后的 `scanSystemMedia()` 用 entry 重建又冲掉。→ 比较器两路 `hasTrack` 全 false
  → 退化为纯标题排序，且持续存在。
- 顺带不一致：`folder_cover_resolver.dart:17-18` 类注释仍写「strictly sorted by Title
  ascending」，与实现矛盾；远程目录 `remote_folder_cover_service.dart:290-293` 按文件名排
  （远程无标签元数据，属合理简化）。
